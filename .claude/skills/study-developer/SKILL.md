# 개발자 역할 (5분 학습)

이 스킬은 `docs/rule.md` 규칙 2의 4종 에이전트 역할 중 **개발자(Developer)**를 재현한다. 이 프로젝트는 실제로는 대부분 대화 중 바로 기능 요청 → 구현 → 배포로 이어지므로, ADR 갱신과 코드 구현 사이에 별도 승인 게이트를 강하게 요구하지 않는다. 다만 예산/플랫폼처럼 `docs/ceo_prompt.md`의 근본 제약을 뒤집는 큰 방향 전환이면 반드시 먼저 확인한다.

## 1단계 — 아키텍처 결정 문서 (해당하는 경우만)

작은 기능 추가·버그 수정처럼 기존 아키텍처를 벗어나지 않는 작업은 이 단계를 건너뛰고 바로 코드로 간다. 새 인프라(새 테이블, 새 외부 서비스, 새 데이터 흐름)를 도입할 때만 `docs/architecture_decision.md`를 갱신한다.

- **입력:** `docs/feature_definition.md`의 관련 F-ID.
- **작업:** 기존 `docs/architecture_decision.md`의 관련 섹션을 Edit로 갱신한다(전체 재작성 아님) — 플랫폼 선택 / 프론트엔드 스택 / 백엔드·데이터 저장 / AI·LLM 통합 / 핵심 데이터 모델 / 시스템 흐름도 / 리스크·트레이드오프.
- **금지:** 기능 정의서에 없는 기능을 새로 만들어내는 것. `docs/ceo_prompt.md`의 제약(무료 티어 등)을 뒤집는 것 — 뒤집어야 한다면 먼저 사용자에게 확인한다.
- **자기검증:**
  1. 관련 F-ID가 요구하는 데이터·흐름이 데이터 모델·흐름도에 반영됐는가?
  2. 예산/플랫폼 제약을 지켰는가?
  3. 기능 정의서의 "미결 항목"을 이 단계에서 구체값으로 확정했는가?
  4. 기능을 임의로 추가하지 않았는가?

## 2단계 — 코드 구현

- **입력:** 관련 F-ID + (있다면) 갱신된 ADR.
- **작업:** 실제 코드를 작성한다.
- **검증:** `npx tsc --noEmit`으로 타입체크, 프론트엔드 변경이면 `npm run build`로 빌드까지 확인한다. UI 변경은 가능하면 실제로 띄워서(`npm run dev` 또는 빌드 결과물) 눈으로 확인한다 — 타입체크만으로는 시각적 회귀를 못 잡는다. 이 프로젝트엔 아직 자동화된 테스트(`test` 스크립트)가 없다(아래 "참고" 참조).
- **배포:** `CLAUDE.md`의 프로젝트 지침대로, 코드를 변경했으면 배포 여부를 묻지 말고 `npm run build && npx wrangler deploy`를 자동으로 실행한다. DB 시드/마이그레이션만 바꿨다면(코드 변경 없음) 배포는 필요 없고, `supabase/migrations` 또는 `supabase/seed`에 파일만 추가한 뒤 "사용자가 Supabase SQL 에디터에서 직접 실행해야 함"을 커밋 메시지나 보고에 명시한다 — 이 저장소엔 서비스 롤 키가 없어 DB에 직접 접근할 수 없다.
- **금지:** 기능 임의 추가. ADR에서 정하지 않은 새 기술 스택 도입.
