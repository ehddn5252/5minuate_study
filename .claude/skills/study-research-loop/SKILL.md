# 연구-기획-구현 루프 (5분 학습)

`study-planner` → `study-fo` → `study-developer` 세 역할을 한 사이클 안에서 순서대로 실행하되, Planner의 입력을 "사용자 요구사항"이 아니라 **웹 검색으로 찾은 아이디어**로 바꾼 자율 루프다. 사용자가 "문서 → 바로 구현까지, 멈추라고 할 때까지 계속"이라고 명시적으로 요청했으므로, 이 루프는 `study-planner`/`study-fo`가 원래 요구하던 승인 대기 없이 한 사이클 안에서 끝까지 진행한다.

## 매 사이클 절차

1. **리서치 (Planner 역할 시작)**: `docs/ceo_prompt.md`의 비전("공부를 해야하지만 게으른 사람을 위한 공부 앱", 목표 이탈 방지)과 현재 제품 형태(목표·퀴즈·커리큘럼·스킨·마스코트·학원 모드, `git log --oneline -20`으로 최근 방향 확인)를 먼저 파악한다. 그 다음 WebSearch로 다음 중 한 방향을 좁혀서 검색한다 — 매 사이클 같은 검색어를 반복하지 않는다:
   - 학습과학/교육심리 기법(간격 반복, 인출 연습, 능동 회상, 습관 형성, 동기부여 넛지 등)이 이 앱의 기존 메커니즘(라이트너 상자, 오답노트, 배지, 연속 학습일)에 어떻게 더 적용될 수 있는지
   - Duolingo·말해보카 등 이미 이 코드베이스가 오마주하고 있는 앱들의 구체적 UX 패턴(커밋 로그에 "듀오링고/말해보카 오마주"로 언급된 것들) 중 아직 없는 것
   - PWA/모바일 웹 학습 앱의 접근성·성능·오프라인 지원 관련 모범 사례
2. **기획 초안 (Planner)**: 찾은 아이디어 중 이 프로젝트의 비전·성공기준과 정렬되는 것 하나를 골라 `docs/planning_document.md`의 관련 섹션에 짧게 반영한다. `study-planner` 스킬의 "먼저 확인할 것"(문서가 v1.0에 멈춰 있고 "5분 내 완결"은 폐기된 원칙) 경고를 그대로 따른다.
3. **기능 정의 (FO)**: Planner의 초안을 받아 `study-fo` 스킬대로 `docs/feature_definition.md`에 새 F-ID를 추가한다. `study-fo` 스킬의 F-ID 번호 확인 절차(코드 주석 + 문서 양쪽 확인)를 그대로 따른다 — 코드 주석 grep만 믿으면 번호가 겹칠 수 있다(사이클 1에서 실제로 겹칠 뻔함, F-47은 이미 "목표 삭제" 기능에 쓰여 있었음). **단, 이번 사이클이 사용자 기능이 아니라 개발 도구/프로세스(예: 빌드 설정, 린트 설정) 수정이면 F-ID를 억지로 붙이지 않는다** — feature_definition.md의 F-ID 템플릿(사용자 입력/시스템 처리/사용자 출력)은 사용자 기능 전용이다. 이런 경우 이 스킬 파일의 "지금까지 이 루프가 반영한 것" 기록에만 남기고 넘어간다(사이클 7 사례 참고).
4. **논의 (Planner ↔ FO)**: FO가 작성한 F-ID가 Planner의 원래 의도·비전과 어긋나지 않는지, 혹은 기술적으로 이 스택(PWA+Supabase+Gemini+Cloudflare Workers, 무료 티어)에서 실현 가능한지 짧게 재검토한다. 어긋나면 F-ID를 조정한다. 이 저장소엔 사람이 실시간으로 없으므로 이 "논의"는 스스로 두 관점을 번갈아 점검하는 자기검증이다.
5. **구현 (Developer)**: `study-developer` 스킬대로 진행한다. 필요하면 `docs/architecture_decision.md`를 갱신하고, 코드 또는 콘텐츠(예: `docs/english_content_spec.md` 기준 시드 데이터)를 작성한다.
6. **검증**: `npx tsc --noEmit`, `npm run build` 통과 필수. UI 변경이면 가능한 범위에서 실제로 렌더링해 확인한다.
7. **배포/커밋**: 코드가 바뀌었으면 `CLAUDE.md` 지침대로 `npm run build && npx wrangler deploy`까지 자동 실행한 뒤 커밋한다. 콘텐츠(DB 시드)만 추가했다면 배포는 생략하고 커밋 메시지에 "Supabase SQL 에디터에서 사용자가 직접 실행 필요"를 명시한다.
8. **보고**: 이번 사이클에서 무엇을 검색했고, 왜 그 아이디어를 골랐고, 문서에 어떻게 반영했고, 실제로 뭘 구현했는지 짧게 보고한다. 매 사이클 전체를 장황하게 설명할 필요는 없지만 "무엇을 왜 선택했는지"는 항상 남긴다.

## 스코프 가드레일 (필수)

- `docs/ceo_prompt.md`의 비전(게으른 사람이 목표를 포기하지 않게)과 무관한 아이디어는 채택하지 않는다. 비목표 항목은 현재 비어있으므로(2026-08-20 기준) 대신 **기존 제품의 실제 형태**(목표 관리·퀴즈·커리큘럼·스킨·학원 모드)를 암묵적 스코프로 삼는다 — 완전히 새로운 제품 축(예: 소셜 네트워크, 커머스)을 만들지 않는다.
- 한 사이클에 아이디어 하나만 채택한다. 검색 결과가 여러 개 유망해도 다음 사이클로 미룬다.
- 예산 제약(무료 티어)을 벗어나는 아이디어(유료 API, 유료 인프라)는 채택하지 않는다.
- 이미 있는 기능의 재발명이 아닌지 `src/`를 먼저 확인한다.
- **그 기능이 실제로 켜져 있는지도 확인한다.** 코드가 존재한다고 해서 그 코드가 실행되는 건 아니다
  (사이클 5에서 `services/notification.ts` 전체가 CEO 요청으로 비활성화돼 App.tsx가 아예 호출하지
  않는 상태였는데 이를 구현 다 끝내고 배포 직전에야 발견함). 구현 착수 전에 관련 모듈이 실제
  진입점(App.tsx, 라우터, 다른 화면)에서 import/호출되는지 `grep -rn "from.*'해당모듈경로'" src/`로
  먼저 확인한다.

## 루프 지속/중단

`/loop`(dynamic mode, 약 5분 간격)로 실행한다. 사용자가 "멈춰"라고 할 때까지 계속하기로 합의했으므로(2026-08-20), 스스로 판단해 멈추지 않는다 — 다만 같은 사이클이 연속으로 실패하거나(빌드 실패 반복 등) 더 이상 스코프 안에서 채택할 아이디어를 못 찾으면 그 사실을 사용자에게 명확히 알리고, 다음 지시를 기다린다.
