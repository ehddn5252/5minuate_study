## 2. `rule.md` — CEO-Level AI Agent 오케스트레이션 프롬프팅 규칙집

> 멀티 에이전트로 제품을 만들 때 매번 재사용하는 프롬프팅 규칙.
> 원칙: **CEO는 WHAT/WHY만, 에이전트는 HOW를.** 헤더(인터페이스)는 사람이, 구현(.c)은 에이전트가.

### 규칙 0. 시작 전 체크리스트

- [ ] 재사용 자산(에이전트 정의·I/O 계약·도구·루브릭)이 영구 저장소에 있는가
- [ ] 이번 프로젝트 전용 저장 경로가 분리됐는가
- [ ] 일일 예산 캡 / 사이클 제한 / no-progress 중단이 설정됐는가
- [ ] 모든 에이전트가 샌드박스 + 최소 권한으로 격리됐는가
- [ ] 휴먼 게이트 2곳(기획 승인 / 아키텍처 승인)이 워크플로에 박혀 있는가

### 규칙 1. CEO 프롬프트 작성 규칙

**✅ 넣어야 하는 것 (WHAT & WHY)**
| 항목 | 설명 |
|------|------|
| 비전 한 문장 | "배민 같은 음식 배달 앱" |
| 핵심 가치 | 가장 중요한 단 하나 (예: 주문 후 예상시간 정확도) |
| 제약 | 예산 · 플랫폼 · 규제 · 보안 |
| 성공 기준 | 무엇이 되면 "완료"인지 측정 가능하게 |
| 비목표 (Non-goals) | **안 할 것** 명시 → 범위 폭주 방지 |

**❌ 넣지 말아야 하는 것 (HOW)**
- 구체적 기술 스택 선택 → 개발자 에이전트의 일
- 화면 단위 기획 → 기획자 에이전트의 일
- 함수 단위 명세 → FO/개발자의 일

**분량 규칙**
> A4 1장 이내 + 비목표 명시. 추상화 레벨이 `for` 루프까지 내려가면 잘못 쓴 것.

**CEO 프롬프트 템플릿 (복붙용)**
```
[제품 비전]
한 문장으로:

[핵심 가치 / 차별점]
가장 중요한 단 하나:

[반드시 지킬 제약]
- 예산:
- 플랫폼:
- 규제/보안:

[성공 기준]
이게 되면 성공이다 (측정 가능하게):

[비목표 — 이번엔 안 한다]
-
-

[휴먼 게이트]
- 기획 완료 시 내 승인 받고 진행
- 아키텍처 확정 시 내 승인 받고 개발 착수
```

### 규칙 2. 에이전트 역할 정의 규칙 (재사용 핵심 자산)

> 각 에이전트는 **시스템 프롬프트 + 입출력 계약(I/O Contract) + 권한 범위**로 정의한다.
> 한 번 만들면 프로젝트마다 재사용한다.

**공통 골격**
```
[역할] 너는 ___ 에이전트다.
[입력] 이전 단계에서 ___ 형식으로 받는다.
[작업] ___ 를 수행한다.
[출력] 다음 단계가 쓸 수 있게 ___ 형식(JSON Schema)으로 낸다.
[금지] 너의 범위를 넘는 ___ 는 하지 않는다.
[자기검증] 출력 전 "요구사항 충족? 누락? 상위 의도와 정렬?" 스스로 점검한다.
```

**4종 에이전트 역할 경계**
| 에이전트 | 입력 | 출력 | 하지 말 것 |
|----------|------|------|-----------|
| **기획자(Planner)** | CEO 비전 | 기획 문서 | 기능/구현 명세 |
| **기능 FO** | 기획 문서 | 기능 정의서 | 기술 스택 결정 |
| **개발자(Developer)** | 기능 정의서 | 개발 방식 결정 + 코드 | 기능 임의 추가 |
| **테스터(Tester)** | 코드 + 기능 정의서 | TC + 테스트 결과 + 빌드 확인 | 코드 직접 수정 |

### 규칙 3. 저장 / RAG 규칙

> **철칙: RAG용 정제 지식과 세션 백업 원본을 절대 섞지 않는다.**
> - 세션 백업 = 감사·추적용 **원본** (통째로 보관)
> - RAG = 에이전트가 참조할 **정제·구조화된 결정사항만** (요약해서 넣기)
> 원본 대화를 통째로 RAG에 넣으면 노이즈 폭발.

**저장 구조**
```
project-factory/
├── agents/            # [영구] 역할 정의
│   ├── planner/system.md
│   ├── feature-owner/system.md
│   ├── developer/system.md
│   ├── tester/system.md
│   └── _contracts/    # 에이전트 간 I/O 스키마
├── tools/             # [영구] 도구 래퍼 + 권한 정책
├── rubrics/           # [영구] 평가 루브릭
├── knowledge-base/    # [영구→갱신] RAG용 정제 지식
└── projects/
    └── <project>/     # [프로젝트별]
        ├── 01-planning/
        ├── 02-features/
        ├── 03-architecture/
        ├── 04-code/
        ├── 05-tests/
        └── sessions/  # 세션 백업 (원본)
```

### 규칙 4. 방향성 검증 규칙 (AI 방법론)

| 방법 | 규칙 |
|------|------|
| **LLM-as-Judge** | 생성 에이전트와 평가 에이전트를 **분리**. 자기 결과 자기 평가 금지 |
| **Reflection** | 출력 전 self-critique 1회 강제 ("충족? 누락?") |
| **계층적 정렬 검증** | 단계마다 상위 의도 대비 검증: 비전→기획→기능→구현→TC 커버리지 |
| **Traceability** | 상위 의도가 하위로 내려가며 변질되지 않는지 추적 |
| **Human Gate** | 큰 비용 발생 단계(개발 착수) 직전엔 사람 최종 승인 |

**검증 프롬프트 템플릿**
```
[평가 대상] <산출물>
[기준] <rubric>
[질문] 이 산출물이 상위 의도와 정렬되는가? 0~10 점수 + 근거 + 누락 항목.
[임계값] N점 미만이면 반려하고 사유를 생성 에이전트에 반환.
```

### 규칙 5. 권한 / 안전 규칙 (⚠️ 절대 양보 금지)

> **"개발 위해 모든 권한 부여"는 보안·비용 양쪽에서 매우 위험.**

| 규칙 | 내용 |
|------|------|
| 최소 권한 | least privilege. 작업별로 필요한 만큼만 |
| 샌드박스 격리 | 컨테이너 격리 안에서만 실행 |
| 네트워크 화이트리스트 | 허용 도메인만 |
| Watchdog | 폭주 프로세스는 죽일 수 있어야 함 (토큰/시간 상한 = circuit breaker) |
| no-progress 감지 | 같은 실패 무한 재시도 차단 |

> 임베디드 watchdog과 같은 개념 — 무한 루프·의도치 않은 삭제·외부 호출 폭주를 막는다.

### 규칙 6. 비용 규칙

| 전략 | 규칙 |
|------|------|
| **모델 티어링** | 추론 중요(방향·아키텍처) = 강한 모델 / 단순 작업(코드생성·테스트·변환) = 빠르고 싼 모델 |
| **프롬프트 캐싱** | 반복되는 시스템 프롬프트·RAG 컨텍스트는 캐싱 |
| **컨텍스트 압축** | 전체 대화 X → "결정사항 요약"만 다음 에이전트에 전달 |
| **예산 가드레일** | 프로젝트별·일별 토큰/비용 캡 + 초과 시 hard stop |
| **사이클 제한** | "하루 종일 자동화"엔 반드시 사이클 횟수 제한 동반 |

> 출력 토큰이 입력보다 비싸고, 멀티 에이전트는 메시지가 곱셈으로 늘어난다.
> 최신 모델별 단가·캐싱 정책은 https://docs.claude.com 에서 확인.

**한 줄 요약 규칙**
> CEO는 인터페이스만 정의하고, 에이전트는 구현한다.
> 재사용 자산과 프로젝트 산출물을 분리하고, RAG와 세션백업을 섞지 않는다.
> 검증은 생성/평가 분리로, 권한은 최소로, 비용은 캡으로 막는다.
> 완전 무인이 아니라, 휴먼 게이트 2곳을 둔 반자동이 현실적 최적이다.

## 3. `planning_document.md` — 기획 문서 v1.0

> 작성 주체: Planner Agent
> 작성일: 2026-06-27
> 다음 단계: FO(Feature Owner) 에이전트에게 전달

### 1. 타겟 사용자 (페르소나)

**페르소나 A — "미루는 직장인" 지훈 (29세)**
- 상황: 자격증 취득이나 업무 지식 보충이 필요하다는 걸 알지만, 퇴근 후 공부를 시작하는 것 자체가 가장 큰 장벽이다.
- 행동 패턴: 공부 앱을 여러 번 설치했지만, 거창한 계획을 세우다 지쳐 며칠 안에 포기한다.
- 핵심 불편: "오늘 딱 5분만 하면 된다"는 확신이 없으면 앱을 열지 않는다.
- 바라는 것: 스스로를 강제할 외부 압력과, "오늘도 했다"는 소소한 성취감.

**페르소나 B — "시험 벼락치기형" 수아 (22세, 대학생)**
- 상황: 시험·발표 2주 전에야 공부를 시작하고, 방대한 분량 앞에서 무엇부터 해야 할지 모른다.
- 행동 패턴: 교재를 정리하는 데 시간을 다 쓰고 막상 내용을 외우지 못한다.
- 핵심 불편: 정리와 암기를 따로 해야 해서 시간이 두 배 든다.
- 바라는 것: 입력한 내용이 자동으로 정리되고, 바로 테스트까지 이어지는 흐름.

### 2. 핵심 사용자 여정 (User Journey)

> 목표: 목표 설정 → 오늘의 학습 → 테스트 → 독려 루프가 한 세션 5분 이내에 완결되어야 한다.

**단계 1 — 목표 설정 (최초 1회)**
1. 사용자가 "무엇을 공부할지(주제·자료)"와 "언제까지 끝낼지(기한)"를 입력한다.
2. 앱이 기한과 분량을 분석해 일일 학습 단위를 제안한다.
3. 사용자가 단위를 확인·조정하고 목표를 확정한다.

감정 포인트: 목표를 등록하는 순간 "이미 시작했다"는 느낌을 주어야 한다.

**단계 2 — 오늘의 학습 (매일 반복)**
1. 앱이 오늘 학습해야 할 분량을 단위로 제시한다.
2. 사용자는 해당 내용을 읽거나, 앱이 핵심만 요약한 버전을 제공받는다.
3. 읽기가 끝나면 곧바로 테스트로 전환된다.

감정 포인트: "오늘 분량이 이것뿐이야?"라는 가벼움을 느껴야 한다.

**단계 3 — 테스트**
1. 학습한 내용 기반의 짧은 문제(2~5문항)가 제시된다.
2. 사용자가 답변하면 즉시 정오답 피드백을 받는다.
3. 오답은 간결한 해설과 함께 다음 세션에 재등장한다.

감정 포인트: "나 방금 공부했고, 맞혔다"는 즉각적 보상.

**단계 4 — 독려 루프 (목표 이탈 방지)**
1. 사용자가 하루라도 학습을 건너뛰면 알림·메시지로 재참여를 유도한다.
2. 연속 달성 스트릭과 목표 달성률을 시각화해 포기 비용을 높인다.
3. 목표 기한이 위협받을 경우 "오늘 한 번만 더" 형태의 긴급 독려를 제공한다.

감정 포인트: 앱이 나를 포기하지 않는다는 느낌.

**단계 5 — 목표 완료**
1. 기한 내 모든 학습·테스트를 마치면 완료 경험을 제공한다.
2. 다음 목표 설정으로 자연스럽게 연결된다.

### 3. 핵심 경험 원칙 (UX 원칙)

1. **"5분 내 완결"이 기본값** — 모든 일일 세션은 5분 안에 학습과 테스트가 끝나도록 설계한다. 사용자가 길이를 선택하게 하지 않는다.
2. **시작 마찰 제로** — 앱을 열면 "오늘 할 것"이 바로 보여야 한다.
3. **포기를 구조적으로 막는다** — 사용자의 의지력에 의존하지 않는다. 알림, 스트릭, 달성률 시각화 등 외부 장치가 목표를 지속시킨다.
4. **칭찬은 빠르게, 오답은 부드럽게** — 정답 피드백은 즉각적·긍정적, 오답은 "다음에 다시 나온다"는 자연스러운 반복 학습으로 처리.
5. **입력 최소화, 결과 최대화** — 사용자는 주제와 기한만 입력. 나머지(분량 분배, 요약, 문제 생성)는 앱이 처리.

### 4. 주요 기능 영역

- **목표 관리 영역**: 목표 생성·수정·완료·비활성화 흐름
- **학습 영역**: 원문 제공, 핵심 요약, 복습 우선순위 조정
- **테스트 영역**: 즉각 피드백, 오답 누적, 반복 출제 로직
- **독려 및 동기 부여 영역**: 알림, 연속 달성 스트릭, 달성률 시각화, 긴급 독려 메시지

### 5. 성공 지표

| 지표 | 정의 | 목표값 |
|------|------|--------|
| 세션 완료 시간 | 학습 시작부터 테스트 완료까지 실제 소요 시간 | 중앙값 5분 이하 |
| 일일 세션 완료율 | 앱을 열어 학습+테스트를 모두 마친 사용자 비율 | 60% 이상 |
| 7일 연속 달성율 | 목표 설정 후 7일 연속으로 세션을 완료한 사용자 비율 | 40% 이상 |
| 목표 완주율 | 설정한 기한 내에 학습 목표를 완료한 사용자 비율 | 30% 이상 |
| 첫 세션 시작까지의 시간 | 목표 설정 완료 후 첫 학습 세션을 시작하기까지의 시간 | 당일 내 80% |

### 6. 범위 외 (Non-goals)

- 소셜 기능: 친구 공유, 랭킹, 그룹 스터디 등 타인과의 비교·경쟁 기능
- 커리큘럼 직접 판매: 콘텐츠 마켓플레이스, 강의 구독 등 플랫폼 비즈니스 모델
- 심층 분석 대시보드: 학습 패턴의 통계적 분석, 주간·월간 리포트 등
- 오프라인 완전 지원: 네트워크 없이 모든 기능이 동작하는 오프라인 퍼스트 설계
- 긴 학습 세션 최적화: 30분~1시간 단위의 집중 학습 모드
- 자격증·시험별 특화 콘텐츠 제공: 앱이 직접 검수한 공식 문제집·교재 제공

## 4. `feature_definition.md` — 기능 정의서 v1.0

### 목차

2. 학습 영역 — F-07 오늘의 학습 분량 제시 / F-08 핵심 요약 제공 / F-09 복습 우선순위 조정 / F-10 학습 세션 완료 처리

### 1. 목표 관리 영역

**F-01 목표 생성** — 사용자가 공부 주제와 기한을 입력해 학습 목표를 등록한다.
- 입력: 공부 주제(필수, 최대 100자) · 기한(필수, 오늘 이후) · 학습 자료(선택)
- 처리: 유효성 검사 → 남은 일수 계산 → 일일 학습 단위 산출(F-02) → 상태 "진행 중" 저장
- 규칙: 진행 중 목표는 동시에 최대 3개까지. 초과 시 생성 차단 + 안내.
- 검증: 과거 날짜 기한 입력 시 저장 안 됨 / 생성 후 오늘의 학습으로 즉시 이동 가능 / 3개 초과 시 안내 메시지 표시

**F-02 일일 학습 단위 제안 및 확정** — 기한·분량을 분석해 하루 학습량을 제안하고 사용자가 확정한다.
- 규칙: 하루 분량은 5분 완결 기준으로 자동 조율(사용자가 직접 조정 불가). 남은 일수 1일이면 전체 분량을 단일 세션으로 압축.
- 검증: 기한이 다르면 제안 분량도 다르게 산출 / 자료 없이 주제만 있어도 분량 제안됨

**F-03 목표 수정** — 진행 중인 목표의 기한 또는 주제를 변경한다.
- 규칙: 기한을 과거로 변경 불가. 기한 단축 시 하루 분량 증가 가능성 안내(단, 5분 완결 유지). 완료된 세션 기록은 유지.
- 검증: 기한 변경 후 남은 세션 재계산 / 과거 날짜 변경 시 오류 / 완료 세션 기록 유지

**F-04 목표 완료 처리** — 기한 내 모든 세션 완료 시 목표를 완료 상태로 전환한다.
- 규칙: 완료 상태는 "진행 중"으로 되돌릴 수 없음. 완료 화면은 최초 1회만 표시.
- 검증: 마지막 세션 완료 시 자동으로 완료 화면 표시 / 완료 목표는 진행 중 목록에서 제거되고 이력으로 분류

**F-05 목표 비활성화(포기)** — 사용자가 목표를 더 진행하지 않기로 선택해 비활성화한다.
- 규칙: 2단계 확인 필요. 재활성화 미지원. 비활성화 후 진행 중 목표 슬롯 1개 증가(3개 제한 해제).
- 검증: 단순 탭 1회로 비활성화되지 않음 / 비활성화 후 알림 중단 / 진행 기록은 이력에서 조회 가능

**F-06 목표 현황 조회** — 진행 중 목표와 완료·비활성화 이력을 한눈에 파악한다.
- 규칙: 진행 중 목표 없으면 생성 유도 화면. 달성률은 정수 퍼센트. 심층 통계는 Non-goal.
- 검증: 목표 없을 때 생성 유도 표시 / 각 카드에 달성률·남은 일수·오늘 완료 여부 표시

### 2. 학습 영역

**F-07 오늘의 학습 분량 제시** — 앱 진입 시 오늘 학습할 내용을 즉시 표시한다.
- 규칙: 메뉴 탐색 없이 첫 화면에 즉시 노출(시작 마찰 제로). 예상 소요 시간은 항상 "약 5분" 고정 표시. 완료 여부는 당일 자정 기준 초기화.
- 검증: 앱 실행 후 별도 탐색 없이 오늘 학습 표시 / 이미 완료 시 완료 상태 표시(중복 실행 방지)

**F-08 핵심 요약 제공** — 오늘 학습 내용을 5분 내 소화 가능한 핵심 요약으로 변환한다.
- 규칙: 요약은 사용자가 편집·길이 조정 불가(자동 제공). 항목 최대 7개. 이탈 후 재진입 시 요약 화면부터 재개.
- 검증: 요약 항목 7개 이하 / 이탈 후 재진입 시 요약 화면부터 재개 / 원문 없이 주제만 있어도 요약 생성

**F-09 복습 우선순위 조정** — 이전 세션의 오답·미완료 항목을 오늘 학습에 자동 편입한다.
- 규칙: 복습 항목이 오늘 전체 분량의 50%를 초과하지 않음(신규 학습 최소 50% 보장). 정답 처리된 항목은 복습 대상에서 제거.
- 검증: 오답 항목이 다음 세션에 포함됨 / 복습 비중 50% 이하 / 정답 처리 후 재등장하지 않음

**F-10 학습 세션 완료 처리** — 학습과 테스트를 모두 마치면 세션 완료를 기록하고 성취 피드백을 제공한다.
- 규칙: 학습만 하고 테스트를 건너뛰면 완료로 처리하지 않음. 완료 시각은 당일 자정 이전이어야 당일 완료로 인정.
- 검증: 학습+테스트 모두 완료해야 세션 완료 기록 / 완료 후 스트릭 갱신 / 완료 화면 후 홈으로 이동

### 3. 테스트 영역

**F-11 퀴즈 생성** — 오늘 학습 내용을 기반으로 2~5개의 짧은 퀴즈 문항을 자동 생성한다.
- 규칙: 문항 수 최소 2개~최대 5개(사용자 선택 불가). 오답 데이터를 반영해 오답 항목 포함. 생성 실패 시 기본 문항으로 대체.
- 검증: 테스트 시작 시 2개 이상 문항 생성 / 5개 초과 안 함 / 1문항씩 표시 + 진행 상태 노출

**F-12 답변 제출 및 즉시 피드백** — 답변 제출 시 즉시 정오답을 알리고 간결한 해설을 제공한다.
- 규칙: 오답 피드백은 부정적 표현 없이 "다음에 다시 나온다"는 프레임 사용. 단답형은 대소문자·조사·공백 차이를 허용하는 유연한 판정. 시간 제한 없음.
- 검증: 정답 제출 시 1초 이내 피드백 / 오답 피드백에 부정 표현 없음 / 마지막 문항 후 전체 결과 화면 / 단답형 대소문자 차이로 오답 처리 안 됨

**F-13 오답 누적 및 반복 출제** — 오답 문항을 저장하고 이후 세션에서 반복 출제한다.
- 규칙: 오답은 즉시 다음 문항이 아닌 최소 다음 세션부터 재출제. 최대 반복 횟수 제한 없음(정답 처리될 때까지).
- 검증: 오답 문항이 다음 세션에 재출제 / 정답 처리 후 그 다음 세션엔 재출제 안 됨 / 오답 목록 조회 화면에서 확인 가능

### 4. 독려 및 동기 부여 영역

**F-14 이탈 감지 및 재참여 알림** — 하루 세션을 건너뛰면 이를 감지해 재참여 알림을 발송한다.
- 규칙: 알림 발송 시각은 사용자 지정 또는 기본값(저녁 8시). 이미 완료한 날엔 발송 안 함. 하루 동일 목표 알림 최대 2회.
- 검증: 미완료 시 당일 알림 발송 / 완료 시 미발송 / 알림 탭 시 오늘의 학습으로 즉시 이동 / 알림 비활성화 시 미발송

**F-15 연속 달성 스트릭** — 연속으로 세션을 완료한 일수를 추적하고 시각적으로 표시한다.
- 규칙: 스트릭 기준일은 달력 일(00:00~23:59). 목표별로 개별 관리. 초기화 후에도 역대 최고 기록은 유지.
- 검증: 연속 완료 시 매일 1씩 증가 / 미완료 시 0으로 초기화 / 역대 최고 스트릭 유지 / 7일 연속 달성 시 축하 메시지

**F-16 목표 달성률 시각화** — 전체 목표 대비 완료된 세션 비율을 시각적으로 표시한다.
- 규칙: 정수 퍼센트 표시. 기한 대비 달성률이 낮으면 지연 상태 레이블(F-17 트리거). 심층 통계는 Non-goal.
- 검증: 세션 완료 후 즉시 갱신 / 정수 퍼센트 표시 / 지연 상태에서 레이블 표시

**F-17 긴급 독려 메시지** — 기한 위협 또는 연속 이탈 감지 시 강도 높은 독려 메시지를 표시한다.
- 규칙: 2일 이상 연속 미완료 또는 기한 대비 달성률 크게 미달 시 발동. 비난·압박 표현 금지, 공감 중심 문구 사용. 같은 날 동일 목표 독려 최대 1회.
- 검증: 2일 연속 미완료 시 긴급 독려 표시 / 탭 시 오늘의 학습으로 즉시 이동 / 같은 날 2회 이상 표시 안 됨 / 세션 완료 후 메시지 사라짐

| 고려 사항 | PWA | 네이티브 앱 | 순수 웹앱 |

| 무료 배포 | GitHub Pages/Vercel Free | 스토어 등록비($25~$99) | 동일 |
| 알림 지원 | Web Push 지원 | 가능하나 빌드 필요 | 불가 |
| 설치 마찰 | 브라우저에서 직접 설치 | 앱스토어 방문 필요 | 없음 |
| 개발 비용 | 단일 코드베이스 | iOS/Android 빌드 분리 | 낮음 |

PWA 선택 근거: F-14(이탈 감지 알림)에 Push Notification 필수 — 순수 웹앱 불가. 네이티브는 free 제약 위배. PWA는 무료 배포 + 모바일/데스크톱 동일 동작.

### 3. 백엔드 및 데이터 저장 방식 (v1.0 원안: 백엔드 없음)

```
[브라우저 로컬 스토리지] ←→ [React 앱] ←→ [AI API (외부)]
         ↑
  [IndexedDB (대용량 자료)]
```

| 저장 대상 | 저장소 | 이유 |
|-----------|--------|------|
| 목표, 세션, 스트릭, 오답 풀 | localStorage | 구조 단순, 무료, 서버 불필요 |
| 학습 자료 원문 | IndexedDB | localStorage 5MB 한계 회피 |
| AI 생성 요약/퀴즈 캐시 | localStorage | 재생성 방지, 비용 절감 |

배포(원안): GitHub Pages 또는 Vercel Free Tier.
> 이후 실제로는 Cloudflare Workers + Supabase(PostgreSQL, Google OAuth)로 확장 배포됨.

### 4. AI/LLM 통합 방식 — Google Gemini API (Free Tier)

| 기능 ID | 기능명 | AI 역할 | 호출 시점 |
|---------|--------|---------|-----------|
| F-02 | 일일 학습 단위 제안 | 주제+기한 → 하루 학습 단위 계획 생성 | 목표 생성 시 1회 |
| F-08 | 핵심 요약 제공 | 원문/주제 → 불릿 3~7개 요약 | 목표 생성 시 1회, 영구 저장 |
| F-11 | 퀴즈 풀 생성 | 요약 내용 → 객관식/단답 10~20문항 풀 생성 | 목표 생성 시 1회, 영구 저장 |

Gemini 선택 이유: OpenAI/Claude는 Free Tier 없음. Gemini 1.5 Flash는 일 1,500회 무료 한도로 소규모 앱에 충분, 한국어 성능 양호. Ollama는 로컬 GPU 필요해 부적합.

**API 호출 전략 (퀴즈 풀 백업 방식 — v1.1)**
```
[목표 생성 시 — AI 호출 3회로 전부 완결]
1. F-02: 학습 단위 계획 생성 → Goal.dailyPlan
2. F-08: 핵심 요약 3~7개 생성 → Goal.summaryContent
3. F-11: 퀴즈 10~20문항 풀 생성 → Goal.quizPool

[이후 매일 세션 시작 시 — AI 호출 0회]
- summaryContent: Goal에서 즉시 로딩
- 퀴즈 문항: quizPool에서 오답 우선 + 랜덤 선택

[풀 소진 시 — 선택적 추가 호출]
- 모든 문항 마스터 시에만 AI 추가 호출
```
목표당 AI 호출 최대 3회. 일 1,500회 한도 기준 약 5,000명까지 무료 운영 가능.

**프롬프트 설계 원칙 (v1.0 원안)**
- F-08 요약: "다음 학습 자료(또는 주제)를 5분 내 읽을 수 있는 핵심 포인트 3~7개로 요약해 주세요. 각 항목은 1~2문장 이내로 작성하세요."
- F-11 퀴즈 풀: "위 요약 내용을 기반으로 객관식(4지선다) 또는 단답형 문항을 15개 생성해 주세요. 다양한 난이도로 구성하고 JSON 배열로 반환하세요: [{question, type, options, answer, explanation, difficulty}]"
- F-02 계획: "주제: {topic}, 기한: {days}일, 자료 유무: {hasContent}. 하루 5분 이내 완료 가능한 일일 학습 단위를 제안해 주세요."

> 실제 구현 프롬프트(난이도 반영 포함)는 `src/services/gemini.ts` 참고.

### 5. 핵심 데이터 모델 (v1.0 원안)

```typescript
interface Goal {
  id: string;
  topic: string;
  deadline: string;
  status: 'active' | 'completed' | 'inactive';
  createdAt: string;
  completedAt?: string;
  totalSessions: number;
  completedSessions: number;
  streak: number;
  bestStreak: number;
  notificationTime: string;
  notificationEnabled: boolean;
  rawContent?: string;
  dailyPlan: string;
  summaryContent: string;
  quizPoolIds: string[];
}

interface Session {
  id: string;
  goalId: string;
  date: string;
  status: 'pending' | 'in_progress' | 'completed';
  summaryViewedAt?: string;
  completedAt?: string;
  selectedQuizIds: string[];
  quizScore?: number;
  quizTotal?: number;
}

interface Quiz {
  id: string;
  goalId: string;
  sessionId: string;
  question: string;
  type: 'multiple_choice' | 'short_answer';
  options?: string[];
  answer: string;
  explanation: string;
  isWrong: boolean;
  wrongCount: number;
  lastAttemptedAt?: string;
}

interface WrongPool {
  goalId: string;
  quizId: string;
  addedAt: string;
  retryCount: number;
  resolvedAt?: string;
}

interface AppState {
  activeGoalIds: string[];
  lastOpenedDate: string;
  urgentGoalIds: string[];
}
```
> 실제 타입 정의(레벨/커리큘럼 필드 등 이후 확장분 포함)는 `src/types/index.ts` 참고.

### 6. 시스템 흐름도 (요약)

- **전체 사용자 흐름**: 목표 없음 → 목표 생성(F-01) → AI 계획 생성(F-02) → 저장 / 목표 있음 → 홈(F-07) → 학습 시작 → 요약(F-08, 캐시 우선) → 테스트(F-11) → 정오답 피드백(F-12, 오답은 F-13 저장) → 세션 완료(F-10, 스트릭/달성률 갱신) → 3초 후 홈
- **독려 루프**: 매일 저녁 8시 완료 여부 체크 → 미완료 1일: 일반 독려(F-14) → 2일 이상: 긴급 독려(F-17)
- **AI 호출 흐름**: 목표 생성 시 계획 생성 1회 → 학습 세션 시 캐시 있으면 즉시 표시, 없으면 요약+퀴즈 생성 후 저장
- **복습 우선순위(F-09)**: 오답 풀 조회 → 오답 없으면 신규 100% / 오답 있으면 50% 이하는 그대로 포함, 50% 초과는 오답 50%+신규 50%로 강제 조정
