# 에이전트 권한 매트릭스 및 상호 질의 프로토콜

> `docs/rule.md` 규칙 5(최소 권한)와 규칙 4(생성/평가 에이전트 분리, 자기 결과 자기 평가 금지)를
> 이 프로젝트의 실제 스킬(`study-planner`/`study-planner-education`/`study-fo`/`study-developer`/루프 스킬)에 적용한 문서.
> `study-planner`/`study-planner-education`/`study-fo`/`study-developer`/`study-improve-loop`/`study-research-loop` 전부 이 문서를 따른다.
>
> (2026-09-13 추가) `study-planner-education`은 "교육 전문 기획자"로, 일반 Planner와 같은
> `docs/planning_document.md`를 다루지만 **학습과학/교수설계 관점으로만** 판단한다(제품 비전·
> 리텐션 판단은 하지 않음). 두 Planner의 결론이 갈리면 어느 한쪽도 서로를 임의로 덮어쓰지 않고
> FO 또는 사용자(CEO)가 조정한다 — 아래 표의 "Planner" 행은 이 서브세트에도 그대로 적용된다.

## 왜 필요한가

기존 루프 스킬들은 역할 경계를 벗어나는 판단이 필요할 때 "먼저 사용자에게 확인" 하거나(대화형 세션),
자율 루프에서는 같은 컨텍스트 안에서 "이제 FO 관점에서 보면..." 식으로 페르소나만 바꿔 자문자답했다
(`study-research-loop`가 스스로 "사람이 실시간으로 없으므로 이 논의는 스스로 두 관점을 번갈아 점검하는
자기검증"이라고 적어둔 부분). 후자는 `docs/rule.md` 규칙 4가 명시적으로 금지하는 "자기 결과 자기 평가"다 —
같은 컨텍스트가 자기 판단을 자기가 승인하면 편향을 걸러낼 수 없다.

대신: 권한 밖 작업이 필요해지면, 그 권한을 실제로 가진 역할을 **별도 서브에이전트로 호출**해 독립적으로
판단받는다. 사용자에게 매번 묻지 않으면서도(자율성 유지) 자기 자신이 자기를 승인하는 문제도 피한다.

## 권한 매트릭스

| 역할 | 소유 파일 / 결정 | 자가 승인 가능 범위 | 벗어나면 질의할 대상 |
|---|---|---|---|
| **Planner** (`study-planner`) | `docs/planning_document.md`, `docs/ceo_prompt.md`의 비전 서술 | 페르소나 / 유저 저니 / UX 원칙 / 기능 영역 / 성공 지표 / 비목표 갱신 | F-ID 단위 구체 스펙이 필요해지면 → **FO에게 질의**. `ceo_prompt.md`의 근본 제약(예산·플랫폼·규제) 자체를 뒤집는 경우 → **사용자에게 에스컬레이션**(아래 "유일한 예외" 참고) |
| **FO** (`study-fo`) | `docs/feature_definition.md` | F-ID 신설/갱신, 역할 경계(학생/교사 등) 명시, 검증 조건 정의 | 기술 스택/DB 스키마/API/알고리즘 확정이 실제로 필요해지면 → **Developer에게 질의**(구현 가능성 확인). 기획 문서의 비전·비목표와 충돌하는지 애매하면 → **Planner에게 질의** |
| **Developer** (`study-developer`) | `docs/architecture_decision.md`, `src/`, `supabase/` | ADR 갱신, 코드 구현, 이미 승인된 F-ID 범위 내 세부 설계 결정 | `feature_definition.md`에 아예 없는 새 기능이 구현 중 필요해지면 → **FO에게 질의**(F-ID 신설 요청). `ceo_prompt.md`의 제약(무료 티어 등)을 뒤집어야 하면 → **사용자에게 에스컬레이션** |

각 역할의 "자가 승인 가능 범위"는 해당 스킬 파일의 "금지" 절과 동일하다 — 이 표는 "벗어났을 때 어디로
보내는지"만 추가한다.

## 질의 프로토콜 (agent 간 자가승인)

1. 권한 밖 판단이 필요한 지점을 만나면 **작업을 멈추지 말고**, Agent 도구로 해당 권한을 가진 역할을
   서브에이전트로 호출한다. 같은 컨텍스트에서 관점만 바꾸지 않는다 — 실제로 분리된 에이전트를 띄운다.
2. 호출 패턴(예: Developer가 F-ID 신설을 FO에게 질의):

   ```
   Agent({
     description: "FO 승인 질의: F-ID 신설",
     subagent_type: "general-purpose",
     prompt: "5minuate_study 프로젝트의 FO 역할로 판단해줘. 배경: <무엇을 만들려는 중이고 왜 이 기능이
       필요해졌는지>. 현재 docs/feature_definition.md의 최신 F-ID는 <번호>. Skill 도구로 study-fo를
       로드해 그 역할의 기준(자기검증 포함)대로 이 기능에 F-ID를 신설해도 되는지 판단해줘.
       승인이면 F-ID 스펙 초안(한 줄 설명/입력/처리/출력/동작 규칙/검증 조건)까지 작성해서 반환하고,
       반려면 이유를 반환해줘."
   })
   ```
3. 응답 처리:
   - **승인 + 산출물**: 그 산출물(F-ID 초안, ADR 조정안 등)을 실제 문서에 반영한 뒤 원래 하던 작업을 이어간다.
     질의 대상 역할의 자기검증을 거친 결과이므로 다시 자기검증하지 않고 그대로 채택한다.
   - **반려**: 반려 사유를 사용자에게 짧게 보고하고 그 작업은 하지 않는다(질의한 역할이 임의로 우회하지 않는다).
   - **질의 대상도 자기 권한 밖이라고 판단**: 표를 따라 다음 상위 역할에 다시 질의하거나(예: FO가 봐도
     기획 자체를 벗어난다면 Planner로), 더 올라갈 곳이 없고 `ceo_prompt.md` 근본 제약과 충돌하면 사용자에게
     에스컬레이션한다.
4. 질의는 실제로 경계를 넘는 결정이 필요할 때만 한다 — 이미 승인된 F-ID 범위 안의 세부 구현처럼 자기 권한
   안의 일까지 매번 질의하지 않는다(불필요한 서브에이전트 호출 남발 금지, `docs/rule.md` 규칙 6 비용 규칙).

## 사용자 에스컬레이션이 남는 유일한 경우

`docs/ceo_prompt.md`의 근본 제약(예산·플랫폼·규제) 자체를 뒤집는 결정. 이건 어떤 에이전트 역할도 소유하지
않은 사용자(CEO) 고유 권한이라 위임할 대상이 없다 — Planner도 FO도 Developer도 이걸 대신 승인해줄 권한이
없다.

## 적용 범위

`study-improve-loop`와 `study-research-loop`처럼 여러 역할을 한 사이클 안에서 순서대로 실행하는 루프
스킬에서 특히 중요하다. 이전에는 "Planner ↔ FO 논의" 단계를 같은 컨텍스트의 자문자답으로 처리했는데,
앞으로는 실제 경계를 넘는 판단이 나오면 이 문서의 질의 프로토콜대로 Agent 호출로 대체한다.
