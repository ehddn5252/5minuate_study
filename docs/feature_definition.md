## 1. 목표 관리 영역

---

### F-01: 목표 생성

**한 줄 설명:** 사용자가 공부 주제와 기한을 입력해 학습 목표를 등록한다.

**사용자 입력**
| 입력 항목 | 형식 | 필수 여부 |
|-----------|------|-----------|
| 공부 주제 | 자유 텍스트 (예: "정보처리기사 실기", "영어 단어 500개") | 필수 |
| 기한 | 날짜 (오늘 이후) | 필수 |
| 학습 자료 | 텍스트 붙여넣기 또는 파일 첨부 | 선택 |

**시스템 처리**
1. 입력값의 유효성을 검사한다 (주제 공백 여부, 기한이 과거 날짜인지 여부).
2. 기한까지 남은 일수를 계산한다.
3. 학습 자료가 있으면 분량 추정에 활용하고, 없으면 주제만으로 일일 학습 단위를 산출한다 (F-02로 연결).
4. 목표 상태를 "진행 중"으로 설정하고 저장한다.
5. 목표 등록 완료 직후 "이미 시작했다"는 완료 피드백을 제공한다.

**사용자 출력**
- 목표가 생성됐음을 알리는 확인 화면
- "오늘의 학습"으로 바로 이동할 수 있는 진입 버튼 표시

**동작 규칙**
- 기한은 오늘 날짜 이후여야 한다. 오늘 날짜 입력 시 당일 세션 1회로 처리한다.
- 동일 주제의 진행 중 목표가 이미 존재하면 중복 등록 여부를 확인한다. 사용자가 허용하면 별도 목표로 생성한다.
- 주제 텍스트는 최대 100자로 제한한다.
- 학습 자료의 분량이 지나치게 많을 경우(상한선은 구현 시 결정), 경고 없이 자동 분할 처리하지 않고 사용자에게 분할 여부를 묻는다.
- 진행 중 목표는 동시에 최대 5개까지 허용한다. 초과 시 새 목표 생성을 막고 안내 메시지를 표시한다. (`GoalCreateScreen.tsx`의 `MAX_ACTIVE_GOALS`로 구현됨 — 원래 3개였으나 사용자 결정으로 5개로 상향)

**검증 조건**
- [ ] 주제와 기한만 입력하면 목표가 생성된다.
- [ ] 과거 날짜 기한 입력 시 오류 메시지를 표시하고 저장되지 않는다.
- [ ] 목표 생성 후 오늘의 학습 화면으로 즉시 이동 가능하다.
- [ ] 진행 중 목표가 3개일 때 추가 시도 시 안내 메시지가 표시된다.

### F-02: 일일 학습 단위 제안 및 확정

**한 줄 설명:** 앱이 기한과 분량을 분석해 하루 학습량을 제안하고, 사용자가 이를 확정한다.

**사용자 입력**
- F-01에서 받은 주제, 기한, 학습 자료(선택)
- 제안된 단위에 대한 확정 또는 재요청 응답

**시스템 처리**
1. 남은 일수와 총 분량(자료 유무에 따라 추정 또는 산출)을 기반으로 하루 분량을 계산한다.
2. 하루 세션이 5분 이내에 완료될 수 있도록 분량을 조율한다. 총 자료가 많더라도 하루 단위를 5분 기준으로 분할한다.
3. "오늘 학습할 내용 미리 보기"를 1~3줄로 제공한다.
4. 사용자가 확정하면 일정 데이터를 저장한다.

**사용자 출력**
- 제안된 하루 분량 요약 화면 (예: "하루 개념 2개 + 단어 10개")
- 오늘의 학습 내용 미리 보기 1~3줄
- "시작하기" 확정 버튼

**동작 규칙**
- 하루 학습 분량은 5분 완결 기준으로 자동 조율된다. 사용자가 분량을 직접 늘리거나 줄이는 설정은 제공하지 않는다.
- 학습 자료 없이 주제만 입력된 경우, 앱이 주제를 기반으로 기본 학습 단위(예: 개념 카드 2~3개)를 생성한다.
- 남은 일수가 1일인 경우 전체 분량을 단일 세션 내에서 처리 가능한 수준으로 압축한다.
- 사용자가 "다시 제안"을 요청할 수 있으나, 5분 완결 제약은 유지된다.

**검증 조건**
- [ ] 기한이 다를 때 제안되는 하루 분량이 다르게 산출된다.
- [ ] 제안 화면에서 확정 시 해당 분량이 매일 학습에 적용된다.
- [ ] 학습 자료 없이 주제만 입력해도 하루 분량이 제안된다.

---

### F-03: 목표 수정

**한 줄 설명:** 진행 중인 목표의 기한 또는 주제를 변경한다.

**사용자 입력**
- 수정할 목표 선택
- 변경할 항목 및 새 값 (기한, 주제 중 하나 이상)

**시스템 처리**
1. 변경된 기한을 기준으로 남은 일정을 재계산한다.
2. 이미 완료된 세션 데이터는 유지하고, 남은 세션만 재분배한다.
3. 수정 후 다음 세션 내용을 갱신한다.

**사용자 출력**
- 수정 완료 확인 메시지
- 변경된 일정 요약 (남은 일수, 오늘 분량)

**동작 규칙**
- 기한을 과거 날짜로 변경할 수 없다.
- 기한을 앞당길 경우, 하루 분량이 늘어날 수 있음을 사용자에게 안내한다. 단, 최종 분량은 여전히 5분 완결 기준을 유지한다.
- 이미 완료된 세션의 내용은 수정되지 않는다.
- 주제 변경 시 학습 자료가 있는 경우, 기존 자료를 유지할지 새로 입력할지 선택하도록 안내한다.

**검증 조건**
- [ ] 기한 변경 후 남은 세션 분량이 재계산된다.
- [ ] 과거 날짜로 기한 변경 시 오류가 표시되고 저장되지 않는다.
- [ ] 완료된 세션 기록이 수정 후에도 그대로 유지된다.

---

### F-04: 목표 완료 처리

**한 줄 설명:** 기한 내 모든 세션을 마치면 목표를 완료 상태로 전환하고 성취 경험을 제공한다.

**사용자 입력**
- 마지막 세션 완료 (자동 감지, 별도 입력 없음)

**시스템 처리**
1. 목표에 할당된 모든 세션이 완료됐는지 확인한다.
2. 목표 상태를 "완료"로 변경한다.
3. 완료 경험 화면(성취 메시지, 스트릭 결과 등)을 구성한다.
4. 다음 목표 설정 유도 안내를 생성한다.

**사용자 출력**
- 목표 완료 성취 화면 (긍정적 메시지, 완료된 기간·세션 수 요약)
- "다음 목표 설정하기" 진입 버튼

**동작 규칙**
- 기한 내 완료 시와 기한 초과 후 완료 시 성취 메시지를 다르게 표시한다 (기한 초과여도 완료는 긍정적으로 처리).
- 완료 상태 목표는 다시 "진행 중"으로 되돌릴 수 없다.
- 완료 화면은 한 번만 표시되며, 이후 조회 시에는 완료 이력 화면으로 전환된다.

**검증 조건**
- [ ] 마지막 세션 완료 시 자동으로 목표 완료 화면이 표시된다.
- [ ] 완료된 목표가 진행 중 목표 목록에서 사라지고 완료 이력으로 분류된다.
- [ ] 완료 화면에서 다음 목표 설정 화면으로 이동 가능하다.

### F-05: 목표 비활성화(포기)

**한 줄 설명:** 사용자가 진행 중인 목표를 더 이상 진행하지 않겠다고 선택해 비활성화한다.

**사용자 입력**
- 비활성화할 목표 선택
- 비활성화 의사 확인 (2단계 확인)

**시스템 처리**
1. 목표 상태를 "비활성"으로 변경한다.
2. 해당 목표에 대한 알림과 스트릭 계산을 중단한다.
3. 지금까지의 진행 기록(완료 세션 수, 달성률)은 보존한다.

**사용자 출력**
- 비활성화 완료 확인 메시지
- 진행 중 목표 목록에서 해당 목표가 제거됨

**동작 규칙**
- 비활성화는 즉시 확인이 아닌 2단계 확인(예: "정말 중단할까요?")을 거친다.
- 비활성화된 목표는 이력 화면에서 조회 가능하지만 재활성화는 지원하지 않는다.
- 비활성화 후 진행 중 목표 슬롯이 1개 증가한다 (F-01의 최대 5개 제한에서 해제).

**검증 조건**
- [ ] 2단계 확인 없이 단순 탭 한 번으로 목표가 비활성화되지 않는다.
- [ ] 비활성화 후 해당 목표의 알림이 더 이상 발송되지 않는다.
- [ ] 비활성화된 목표의 진행 기록(세션 완료 수)이 이력에서 조회된다.

---

### F-06: 목표 현황 조회

**한 줄 설명:** 진행 중인 목표와 완료·비활성화 이력을 한눈에 파악한다.

**사용자 입력**
- 목표 현황 화면 진입 (탭 이동 또는 버튼)

**시스템 처리**
1. 진행 중 목표 목록을 조회한다.
2. 각 목표의 달성률(완료 세션 / 전체 세션), 남은 일수, 오늘 세션 완료 여부를 계산한다.
3. 완료·비활성화 이력 목록을 조회한다.

**사용자 출력**
- 진행 중 목표 카드 목록 (주제, 달성률 바, 남은 일수, 오늘 완료 여부)
- 완료·이력 섹션 (접기/펼치기 가능)
- 새 목표 추가 진입 버튼

**동작 규칙**
- 진행 중 목표가 없으면 목표 생성 유도 화면을 표시한다.
- 달성률은 소수점 없이 정수 퍼센트(0~100%)로 표시한다.
- 심층 통계(학습 패턴 분석, 주간 리포트 등)는 Non-goal이므로 제공하지 않는다.

**검증 조건**
- [ ] 진행 중 목표가 없을 때 목표 생성 유도 화면이 표시된다.
- [ ] 각 목표 카드에 달성률, 남은 일수, 오늘 완료 여부가 표시된다.
- [ ] 완료 이력이 별도 섹션으로 구분되어 조회된다.

## 2. 학습 영역

### F-07: 오늘의 학습 분량 제시

**한 줄 설명:** 앱 진입 시 오늘 학습할 내용을 즉시 화면에 표시한다.

**사용자 입력**
- 앱 실행 또는 홈 화면 진입 (별도 입력 없음)

**시스템 처리**
1. 진행 중인 활성 목표를 조회한다.
2. 오늘 날짜에 해당하는 학습 단위를 불러온다.
3. 오늘 세션이 이미 완료된 경우, 완료 상태를 표시한다.
4. 아직 완료되지 않은 세션이 있으면 해당 내용을 전면에 표시한다.

**사용자 출력**
- 오늘의 학습 카드 (학습 주제, 예상 소요 시간 "약 5분", 학습 시작 버튼)
- 진행 중 목표가 여러 개면 오늘 미완료 목표를 순서대로 표시

**동작 규칙**
- 앱 진입 시 메뉴 탐색 없이 오늘의 학습이 첫 화면에 바로 보여야 한다 (시작 마찰 제로 원칙).
- 오늘 분량이 없는 날(공휴일, 기한 초과 등)은 완료 메시지 또는 다음 목표 유도를 표시한다.
- 예상 소요 시간은 항상 "약 5분"으로 고정 표시한다 (사용자 이탈 방지).
- 세션 완료 여부는 당일 자정을 기준으로 초기화된다.

**검증 조건**
- [ ] 앱 실행 후 별도 탐색 없이 오늘의 학습 내용이 첫 화면에 표시된다.
- [ ] 오늘 세션을 이미 완료한 경우 완료 상태가 표시되고 중복 실행되지 않는다.
- [ ] 진행 중 목표가 없을 때 목표 생성 유도 화면이 표시된다.

---

### F-08: 핵심 요약 제공

**한 줄 설명:** 오늘 학습할 내용을 5분 내 소화 가능한 핵심 요약으로 변환해 제공한다.

**사용자 입력**
- 학습 시작 버튼 탭 (별도 설정 없음)

**시스템 처리**
1. 오늘 분량에 해당하는 원문 또는 주제 데이터를 불러온다.
2. 핵심 개념·키워드 중심으로 요약 텍스트를 생성한다.
3. 요약 분량이 5분 이내 독해 가능한 수준인지 검토한다.

**사용자 출력**
- 핵심 요약 화면 (불릿 포인트 또는 카드 형식, 3~7항목)
- "다 읽었어요 → 테스트 시작" 버튼

**동작 규칙**
- 요약은 사용자가 편집하거나 길이를 조정할 수 없다. 앱이 자동으로 제공한다 (입력 최소화 원칙).
- 원문이 없고 주제만 있는 경우에도 앱이 주제 기반 핵심 내용을 구성한다.
- 요약 항목은 최대 7개로 제한한다. 항목이 많아질 경우 중요도 순으로 자른다.
- 사용자가 요약 화면에서 이탈(앱 종료 등)했다가 재진입하면 요약 화면부터 재개한다.

**검증 조건**
- [ ] 학습 시작 시 별도 설정 없이 핵심 요약이 표시된다.
- [ ] 요약 항목이 7개를 초과하지 않는다.
- [ ] 요약 화면에서 이탈 후 재진입 시 요약 화면부터 재개된다.
- [ ] 원문 없이 주제만 있는 경우에도 요약이 생성된다.

### F-09: 복습 우선순위 조정

**한 줄 설명:** 이전 세션의 오답 및 미완료 항목을 오늘 학습에 자동으로 우선 편입한다.

**사용자 입력**
- 별도 입력 없음 (시스템이 자동 처리)

**시스템 처리**
1. 오답 누적 데이터(F-13)를 조회한다.
2. 오답 또는 미완료 항목을 오늘 학습 분량에 우선 포함시킨다.
3. 전체 세션 길이가 5분을 초과하지 않도록 오늘 분량을 조율한다. 복습 항목이 많을 경우 신규 항목 수를 줄인다.

**사용자 출력**
- 별도 복습 안내 없이 오늘 요약에 자연스럽게 포함 ("이전에 틀린 내용" 레이블로 구분 표시 가능)

**동작 규칙**
- 복습 우선순위 조정은 사용자에게 노출되지만, 사용자가 조정하거나 끌 수 없다.
- 복습 항목이 오늘 전체 분량의 50%를 초과하지 않도록 한다. 오답이 많아도 신규 학습이 최소 50% 이상 포함된다.
- 한 번 복습에서 정답 처리된 항목은 복습 대상에서 제거된다.

**검증 조건**
- [ ] 이전 세션 오답 항목이 다음 세션 학습에 포함된다.
- [ ] 복습 항목이 오늘 분량의 50%를 초과하지 않는다.
- [ ] 복습에서 정답 처리된 항목은 이후 복습에 재등장하지 않는다.

### F-10: 학습 세션 완료 처리

**한 줄 설명:** 오늘의 학습과 테스트를 모두 마치면 세션 완료를 기록하고 성취 피드백을 제공한다.

**사용자 입력**
- 테스트 마지막 문항 제출 (자동 감지)

**시스템 처리**
1. 오늘 세션의 학습 및 테스트 완료 여부를 확인한다.
2. 세션 완료 시각과 소요 시간을 기록한다.
3. 스트릭 데이터를 갱신한다 (F-15).
4. 달성률을 갱신한다 (F-16).

**사용자 출력**
- 세션 완료 피드백 화면 (긍정 메시지, 오늘 점수, 스트릭 현황)
- "내일도 봐요" 또는 다음 목표 안내

**동작 규칙**
- 세션 완료는 학습(F-08)과 테스트(F-11~F-12) 모두 완료한 경우에만 기록된다. 학습만 하고 테스트를 건너뛰면 완료로 처리하지 않는다.
- 세션 완료 시각은 당일 자정(00:00) 이전이어야 당일 완료로 인정된다.
- 완료 피드백 화면은 자동으로 3초 후 홈 화면으로 전환되거나, 사용자가 수동으로 닫을 수 있다.

**검증 조건**
- [ ] 학습과 테스트를 모두 완료한 경우에만 세션 완료로 기록된다.
- [ ] 세션 완료 후 스트릭 수치가 갱신된다.
- [ ] 완료 피드백 화면이 표시된 후 홈 화면으로 이동된다.

### F-11: 퀴즈 생성

**한 줄 설명:** 오늘 학습 내용을 기반으로 2~5개의 짧은 퀴즈 문항을 자동 생성한다.

**사용자 입력**
- "테스트 시작" 버튼 탭 (학습 요약 화면에서 전환)

**시스템 처리**
1. 오늘의 핵심 요약(F-08)에서 핵심 개념·키워드를 추출한다.
2. 오답 누적 데이터(F-13)를 반영해 오답 항목을 문항에 포함시킨다.
3. 문항 수를 2~5개로 산출한다. 학습 분량이 적으면 2개, 많으면 최대 5개.
4. 문항 형식은 객관식(4지선다) 또는 단답형으로 생성한다.

**사용자 출력**
- 문항 목록 화면 (한 번에 1문항씩 표시)
- 진행 표시 (예: "2/3번째 문항")

**동작 규칙**
- 문항 수는 최소 2개, 최대 5개로 고정한다. 사용자가 문항 수를 선택할 수 없다.
- 같은 문항이 연속 세션에서 동일한 형태로 반복되지 않도록 문항 순서나 선택지를 변형한다.
- 퀴즈 생성 실패(데이터 부족 등) 시 기본 문항("오늘 학습한 주제는 무엇인가요?" 등)으로 대체한다.
- 한 세션에서 동일한 문항이 중복 출제되지 않는다.

**검증 조건**
- [ ] 테스트 시작 시 2개 이상의 문항이 생성된다.
- [ ] 문항 수가 5개를 초과하지 않는다.
- [ ] 퀴즈가 한 번에 1문항씩 표시되고 진행 상태가 보인다.

---

### F-12: 답변 제출 및 즉시 피드백

**한 줄 설명:** 사용자가 문항에 답변을 제출하면 즉시 정오답을 알리고 간결한 해설을 제공한다.

**사용자 입력**
- 선택지 탭 (객관식) 또는 텍스트 입력 후 제출 (단답형)

**시스템 처리**
1. 사용자 답변과 정답을 비교한다.
2. 정오답 여부를 판정한다.
3. 오답인 경우 해당 문항을 오답 목록에 추가한다 (F-13).
4. 다음 문항으로 전환하거나, 마지막 문항이면 세션 완료 처리를 진행한다.

**사용자 출력**
- 정답 시: 즉각적이고 긍정적인 피드백 (예: 정답 표시 + 짧은 칭찬 문구)
- 오답 시: 정답 표시 + 1~2줄 해설 + "다음에 다시 나와요" 안내
- 전체 결과 화면 (마지막 문항 후): 맞힌 수 / 전체 문항 수

**동작 규칙**
- 오답 피드백은 "틀렸다"는 부정적 표현을 사용하지 않는다. "다음에 다시 나온다"는 반복 학습 프레임으로 표현한다 (원칙 4: 오답은 부드럽게).
- 단답형의 경우 대소문자·조사·공백 차이를 허용하는 유연한 정답 판정을 적용한다.
- 피드백 표시 후 다음 문항으로의 전환은 자동(1~2초 후) 또는 사용자 탭으로 진행한다.
- 시간 제한은 없다.

**검증 조건**
- [ ] 정답 제출 시 즉시(1초 이내) 정답 피드백이 표시된다.
- [ ] 오답 피드백에 부정적 표현("틀렸습니다") 없이 해설과 재등장 안내가 표시된다.
- [ ] 마지막 문항 완료 후 전체 결과 화면이 표시된다.
- [ ] 단답형에서 대소문자 차이가 있는 정답이 오답 처리되지 않는다.

---

### F-13: 오답 누적 및 반복 출제

**한 줄 설명:** 오답으로 처리된 문항을 저장하고 이후 세션에서 반복 출제한다.

**사용자 입력**
- F-12에서 오답 처리된 문항 데이터 (자동 수집)

**시스템 처리**
1. 오답 문항을 오답 풀에 저장한다.
2. 다음 세션 퀴즈 생성 시(F-11) 오답 풀에서 우선 문항을 선택한다.
3. 오답 문항에서 정답 처리되면 해당 문항을 오답 풀에서 제거한다.
4. 오답 풀이 가득 찰 경우(상한선은 구현 시 결정) 가장 오래된 오답부터 제거한다.

**사용자 출력**
- 오답 문항 재출제 시 별도 표시 없이 일반 문항과 동일하게 출제 (사용자가 인식하지 못하게 자연스럽게 반복)
- 선택적으로 오답 목록 조회 화면 제공 (문항 내용, 정답, 해설)

**동작 규칙**
- 오답 문항은 즉시 다음 문항에서 재출제되지 않는다. 최소 다음 세션부터 등장한다.
- 동일 문항이 같은 세션 내에 신규 문항과 오답 복습 문항으로 중복 출제되지 않는다.
- 오답이 정답 처리될 때까지 최대 반복 횟수 제한은 두지 않는다.

**검증 조건**
- [ ] 오답 문항이 다음 세션에 재출제된다.
- [ ] 오답 문항에서 정답 처리 후 그 다음 세션에 재출제되지 않는다.
- [ ] 오답 목록 조회 화면에서 저장된 오답 문항을 확인할 수 있다.

### F-14: 이탈 감지 및 재참여 알림

**한 줄 설명:** 사용자가 하루 세션을 건너뛰면 이를 감지하고 재참여를 유도하는 알림을 발송한다.

**사용자 입력**
- 별도 입력 없음 (시스템이 미완료 상태를 자동 감지)

**시스템 처리**
1. 매일 지정된 시각에 당일 세션 완료 여부를 확인한다.
2. 미완료 상태이면 알림을 생성한다.
3. 알림 문구는 단계적으로 강도를 조절한다 (1일 미완료: 가벼운 알림, 2일 이상 연속 미완료: 긴급 독려 F-17로 에스컬레이션).

**사용자 출력**
- 푸시 알림 또는 인앱 알림 (짧은 독려 문구, 탭 시 오늘의 학습 화면으로 직접 이동)

**동작 규칙**
- 알림 발송 시각은 사용자가 최초 목표 설정 시 지정하거나, 기본값(저녁 8시)으로 설정된다.
- 사용자가 알림을 비활성화할 수 있으나, 비활성화 시 포기 위험을 안내한다.
- 이미 세션을 완료한 날에는 알림을 발송하지 않는다.
- 비활성화된 목표에 대한 알림은 발송하지 않는다.
- 하루에 동일 목표에 대한 알림은 최대 2회로 제한한다.

**검증 조건**
- [ ] 세션 미완료 시 당일 알림이 발송된다.
- [ ] 세션 완료 시 당일 알림이 발송되지 않는다.
- [ ] 알림 탭 시 오늘의 학습 화면으로 바로 이동된다.
- [ ] 알림 비활성화 시 알림이 발송되지 않는다.
- [ ] 비활성화된 목표에 대한 알림이 발송되지 않는다.

### F-15: 연속 달성 스트릭

**한 줄 설명:** 연속으로 세션을 완료한 일수를 추적하고 시각적으로 표시한다.

**사용자 입력**
- 별도 입력 없음 (세션 완료 시 자동 갱신)

**시스템 처리**
1. 세션 완료 시 연속 달성 일수를 1 증가시킨다.
2. 하루라도 세션을 미완료하면 스트릭을 0으로 초기화한다.
3. 역대 최고 스트릭을 별도로 저장한다.

**사용자 출력**
- 현재 연속 달성 일수 표시 (홈 화면 또는 세션 완료 화면)
- 역대 최고 스트릭 표시
- 특정 마일스톤(7일, 30일 등) 달성 시 축하 메시지 표시

**동작 규칙**
- 스트릭 카운트 기준일은 달력 일(00:00~23:59)이다. 자정 이후 완료는 다음 날로 처리된다.
- 진행 중 목표가 여러 개인 경우 스트릭은 목표별로 개별 관리한다.
- 스트릭 초기화 후에도 과거 달성 기록(역대 최고 일수, 완료 캘린더)은 삭제되지 않는다.

**검증 조건**
- [ ] 연속 세션 완료 시 스트릭 수치가 매일 1씩 증가한다.
- [ ] 하루 세션 미완료 시 스트릭이 0으로 초기화된다.
- [ ] 역대 최고 스트릭이 초기화 후에도 유지된다.
- [ ] 7일 연속 달성 시 마일스톤 축하 메시지가 표시된다.

---

### F-16: 목표 달성률 시각화

**한 줄 설명:** 전체 목표 대비 완료된 세션 비율을 시각적으로 표시한다.

**사용자 입력**
- 별도 입력 없음 (세션 완료 시 자동 갱신, 화면 진입 시 표시)

**시스템 처리**
1. 완료된 세션 수 / 전체 세션 수를 계산해 달성률(%)을 산출한다.
2. 기한 대비 현재 달성률의 적절성을 평가한다 (예: 기한이 50% 지났는데 달성률이 30%면 지연 상태).
3. 지연 상태면 긴급 독려(F-17)를 트리거한다.

**사용자 출력**
- 달성률 진행 바 또는 원형 그래프 (0~100%)
- 기한 대비 진행 상태 레이블 (예: "정상 진행 중", "조금 뒤처지고 있어요")
- 남은 세션 수, 남은 일수 표시

**동작 규칙**
- 달성률은 정수 퍼센트(소수점 없음)로 표시한다.
- 심층 통계(학습 효율 분석, 요일별 패턴 등)는 Non-goal이므로 제공하지 않는다.
- 기한이 지난 목표는 달성률과 함께 "기한 초과" 레이블을 표시하되, 완료 유도를 포기하지 않는다.

**검증 조건**
- [ ] 세션 완료 후 달성률이 즉시 갱신된다.
- [ ] 달성률이 소수점 없이 정수 퍼센트로 표시된다.
- [ ] 기한 대비 지연 상태에서 지연 레이블이 표시된다.

### F-17: 긴급 독려 메시지

**한 줄 설명:** 기한 위협 또는 연속 이탈 감지 시 강도 높은 독려 메시지를 표시한다.

**사용자 입력**
- 별도 입력 없음 (F-14 또는 F-16의 조건 충족 시 자동 트리거)

**시스템 처리**
1. 다음 조건 중 하나 이상 충족 시 긴급 독려를 발동한다:
   - 2일 이상 연속 세션 미완료
   - 기한까지 남은 일수 대비 달성률이 목표에 크게 미달 (예: 기한의 70%가 지났는데 달성률 40% 미만)
2. 조건 강도에 따라 메시지 톤을 조절한다 (부드러운 독려 → 긴급 독려).
3. 긴급 독려 후 사용자가 세션을 완료하면 독려 상태를 해제한다.

**사용자 출력**
- 인앱 배너 또는 팝업: "오늘 한 번만 더" 형태의 독려 메시지
- 즉시 학습 시작 버튼 (탭 시 오늘의 학습으로 바로 이동)
- 긴급 독려 알림 (F-14 알림보다 강조된 형태)

**동작 규칙**
- 독려 메시지는 비난이나 압박 표현을 사용하지 않는다. "포기 안 했으면 해요", "오늘 딱 5분만" 등 공감 중심 표현을 사용한다.
- 같은 날 동일 목표에 대한 긴급 독려는 최대 1회로 제한한다.
- 비활성화된 목표에는 독려를 발동하지 않는다.
- 사용자가 독려를 무시해도 다음 날 기준으로 재평가한다.

**검증 조건**
- [ ] 2일 연속 미완료 시 긴급 독려 메시지가 표시된다.
- [ ] 독려 메시지 탭 시 오늘의 학습 화면으로 즉시 이동된다.
- [ ] 같은 날 동일 목표에 독려가 2회 이상 표시되지 않는다.
- [ ] 세션 완료 후 독려 메시지가 사라진다.

### F-49: 스트릭 프리즈

**한 줄 설명:** 하루를 건너뛰어도 목표당 1회는 연속 달성 스트릭이 끊기지 않도록 보호한다.

**사용자 입력**
- 별도 입력 없음 (목표 생성 시 자동 지급, 조건 충족 시 자동 소진)

**시스템 처리**
1. 목표를 생성하면 `streakFreezeRemaining`을 1로 초기화한다.
2. 세션 완료 시점에 어제 완료 기록이 없고(스트릭이 끊길 상황), 현재 `streak`가 0보다 크며(지켜줄 스트릭이 실제로 있음), 남은 프리즈가 1개 이상이면 프리즈를 1개 소진하고 스트릭을 정상 연속처럼 +1 한다.
3. 조건을 만족하지 않으면(프리즈 없음, 또는 애초에 스트릭이 0이었음) 기존 로직대로 스트릭을 1로 리셋한다.

**사용자 출력**
- 세션 완료 화면(`SessionCompleteScreen.tsx`)에 "🧊 어제 하루를 쉬었지만 프리즈 덕분에 스트릭이 끊기지 않았어요!" 카드를 조건부로 노출한다(레벨업/마일스톤/뱃지 다음, 깜짝 보상 이전 우선순위).

**동작 규칙**
- 프리즈는 목표당 1개, 소진되면 재충전되지 않는다(재충전 메커니즘은 별도 사이클 과제로 남김 — 아래 "판단 보류" 참고).
- 같은 날 세션을 여러 번 이어가는 경우(alreadyCompletedToday)는 프리즈 판단 대상이 아니다.
- 스트릭이 이미 0인 상태(막 시작했거나 이미 끊긴 상태)에서는 프리즈를 소모하지 않는다 — 지킬 스트릭이 없기 때문.
- `GoalCompleteScreen.tsx`(목표 전체 완료 화면)에는 아직 이 카드를 추가하지 않았다(세션 완료 화면만 우선 적용, 스코프 최소화).

**검증 조건**
- [ ] 목표 생성 시 `streakFreezeRemaining`이 1로 설정된다.
- [ ] 어제를 건너뛰고 오늘 세션을 완료하면(스트릭>0, 프리즈≥1) 스트릭이 끊기지 않고 +1 되며 프리즈가 0으로 줄어든다.
- [ ] 같은 조건에서 프리즈가 이미 0이면 스트릭이 1로 리셋된다.
- [ ] 스트릭이 0인 상태로 어제를 건너뛰면 프리즈를 소모하지 않는다.
- [ ] 세션 완료 화면에 프리즈 사용 카드가 조건부로만 노출된다.

**판단 보류 (다음 사이클 후보)**
- 프리즈 재충전 방법(예: N일 연속 달성마다 1개 추가 지급) — 이번 사이클은 스코프를 "1개 초기 지급"으로 최소화함.
- `GoalCompleteScreen.tsx`(목표 전체 완료)에도 동일 카드를 추가할지.
- 스트릭 표시 UI(홈 화면 등)에 남은 프리즈 개수를 상시 노출할지.

### F-50: 동작 줄이기(prefers-reduced-motion) 대응

**한 줄 설명:** OS/브라우저에서 "동작 줄이기"를 켠 사용자에게는 장식성 애니메이션을 자동으로 끈다.

**사용자 입력**
- 별도 앱 내 설정 없음 — OS/브라우저의 접근성 설정(`prefers-reduced-motion: reduce`)을 그대로 따른다.

**시스템 처리**
1. CSS 미디어 쿼리 `@media (prefers-reduced-motion: reduce)`로 해당 설정 여부를 감지한다.
2. 감지되면 장식성 애니메이션 클래스(`animate-feedback-pop`, `animate-feedback-shake`, `animate-count-up-pop`, `animate-page-enter`, `animate-bounce`)를 전부 무효화한다(`animation: none`).
3. 기능적 의미가 있는 모션(로딩 스피너 `animate-spin`, 녹음 중 표시 `animate-pulse`)은 예외로 두고 그대로 유지한다.

**사용자 출력**
- 별도 UI 없음 — 정답 팝/오답 흔들림/카운트업/페이지 전환/마스코트 바운스가 조용히 사라지고, 나머지 기능은 동일하게 동작한다.

**동작 규칙**
- 순수 CSS로 구현하며 새 의존성이나 런타임 분기 없음.
- 로딩 스피너·녹음 중 표시처럼 상태를 전달하는 모션은 끄지 않는다.
- 버튼 눌림 스케일(`active:scale-*`) 같은 짧고 사용자 주도적인 마이크로 인터랙션은 이번 스코프에서 제외한다(WCAG의 reduced-motion 우려 대상은 주로 자동 재생·큰 폭 모션).

**검증 조건**
- [ ] `prefers-reduced-motion: reduce` 환경에서 `animate-bounce` 요소의 `animationName`이 `none`이 된다.
- [ ] 같은 환경에서 `animate-spin` 요소는 애니메이션이 그대로 유지된다.
- [ ] 설정을 켜지 않은 기본 환경에서는 기존 애니메이션이 전부 그대로 재생된다.

### F-51: 오프라인 상태 안내 배너

**한 줄 설명:** 네트워크 연결이 끊기면 화면 최상단에 짧은 안내 배너를 보여준다.

**사용자 입력**
- 별도 입력 없음 — 브라우저의 `navigator.onLine` 상태와 `online`/`offline` 이벤트를 그대로 따른다.

**시스템 처리**
1. `OfflineBanner` 컴포넌트가 마운트 시 `navigator.onLine`으로 초기 상태를 읽는다.
2. `window`의 `online`/`offline` 이벤트를 구독해 상태가 바뀔 때마다 갱신한다.
3. 오프라인이면 배너를 렌더링하고, 온라인으로 돌아오면 자동으로 사라진다(수동 닫기 없음 — 상태가 곧 UI).

**사용자 출력**
- 로그인 전/후 모든 화면 최상단에 "📶 오프라인 상태예요 — 인터넷 연결을 확인해주세요" 배너(주황색, 일반 흐름 요소로 배치돼 기존 헤더를 가리지 않고 콘텐츠를 자연스럽게 아래로 밀어냄).

**동작 규칙**
- `fixed` 오버레이가 아니라 라우트 콘텐츠 앞의 형제 요소로 렌더링해, 화면마다 헤더와 겹치는 문제 없이 자동으로 레이아웃에 편입된다.
- 로그인 전(`/shorts`, 로그인 화면)과 로그인 후 라우터 트리 양쪽에 각각 마운트해 항상 노출된다.
- 서버 상태를 확인하는 것이 아니라 브라우저의 네트워크 연결 여부만 감지한다 — Supabase/Gemini 서버 자체 장애는 감지 범위 밖(별도 사이클 과제).

**검증 조건**
- [ ] `navigator.onLine`이 `false`가 되고 `offline` 이벤트가 발생하면 배너가 나타난다.
- [ ] `online` 이벤트가 발생하면 배너가 사라진다.
- [ ] 배너가 페이지 콘텐츠를 가리지 않고 자연스럽게 위에 쌓인다.

**판단 보류 (다음 사이클 후보)**
- 서버 자체 장애(네트워크는 있지만 Supabase/Gemini가 응답 안 함) 감지는 별도 과제.
- 오프라인 중 시도한 동작(퀴즈 제출 등)을 큐에 담아뒀다가 재연결 시 자동 재시도할지 여부.

### F-52: PWA 앱 바로가기(매니페스트 shortcuts)

**한 줄 설명:** 설치된 앱 아이콘을 길게 누르면(Android/데스크톱) 홈 화면을 거치지 않고 "복습"·"오답노트"로 바로 진입할 수 있다.

**사용자 입력**
- 홈 화면(OS)에서 설치된 앱 아이콘을 길게 누르기.

**시스템 처리**
1. `vite-plugin-pwa`가 `vite.config.ts`의 `manifest.shortcuts` 배열을 `manifest.webmanifest`에 그대로 반영한다.

### F-56: 첫 실행 시 OS 다크 모드 감지해 배경 스킨 기본값 결정

**한 줄 설명:** 저장된 설정이 전혀 없는 진짜 첫 방문자에 한해, 기기의 다크 모드(`prefers-color-scheme: dark`)가 켜져 있으면 기존에 이미 있던 '차콜' 배경 스킨을 기본값으로 준다.

**사용자 입력**
- 별도 입력 없음 — 앱을 처음 여는 순간 기기 설정을 자동으로 확인.

**시스템 처리**
1. `getAppState()`가 `localStorage`에서 `appState`를 읽었을 때 값이 아예 없으면(=진짜 첫 실행) `window.matchMedia('(prefers-color-scheme: dark)')`를 확인한다.

- 저장 자체를 하지 않는다(메모리상 계산만) — 사용자가 설정 화면에서 뭔가 바꾸기 전까지는 `localStorage`에 아무것도 쓰지 않아, 이후 OS 다크 모드를 끄면 다음 "진짜 첫 실행" 판정 시 다시 라이트 기본값으로 계산된다. 단, 앱을 한 번이라도 쓴 뒤엔(=`appState` 저장된 뒤엔) 이 재계산 자체가 더 이상 일어나지 않는다.

**검증 조건**

- [x] Playwright로 `colorScheme: 'dark'` + 저장된 `appState.bgTheme: 'default'` → 여전히 `'default'`(덮어쓰지 않음) 확인.

**판단 보류 (다음 사이클 후보)**

### F-59: iOS Safari용 홈 화면 추가 안내

**한 줄 설명:** 기존 설치 배너(`InstallBanner.tsx`)는 `beforeinstallprompt` 이벤트에만 의존해 아이폰(iOS Safari) 사용자에게는 영원히 뜨지 않았다 — iOS Safari에서만 "공유 버튼 → 홈 화면에 추가"를 안내하는 문구형 배너를 추가로 보여준다.

**동작 규칙**

### F-65: 학원 공지 안 읽음 배지

**한 줄 설명:** 학생이 "학원" 화면의 "공지" 탭을 열어보지 않아도, 새로 올라온 공지가 몇 건인지 빨간 배지로 미리 보여준다.

**사용자 입력**

**시스템 처리**
1. `utils/storage.ts`에 `getLastSeenAnnouncementAt`/`setLastSeenAnnouncementAt`(localStorage 기반)을 추가 — 학생이 마지막으로 공지 탭을 확인한 시각을 기록한다.
2. 저장된 값이 아예 없으면(이 기능이 막 생긴 시점, 진짜 첫 확인) 지금 있는 공지들의 최신 시각으로 값을 채워 넣고 안 읽음 0건으로 시작한다 — 기능이 추가되자마자 기존 공지가 전부 "안 읽음"으로 잡혀서 갑자기 큰 숫자가 뜨는 걸 막기 위함. 그 이후에 새로 올라오는 공지만 "새 것"으로 집계된다.
3. 저장된 값이 있으면 `공지.createdAt > 마지막 확인 시각`인 것만 세어 배지에 표시한다.
4. "공지" 탭을 누르면 그 시점의 최신 공지 시각으로 `lastSeenAnnouncementAt`을 갱신하고 배지를 즉시 지운다.

**사용자 출력**
- "학원" 화면 진입 시 "공지" 탭 오른쪽 위에 작은 빨간 숫자 배지가 보인다(안 읽은 게 있을 때만). 탭을 누르면 배지가 사라지고, 다음에 또 새 공지가 올라올 때까지 다시 안 뜬다.

**동작 규칙**

- 서버가 아니라 기기 로컬(localStorage)에 저장 — 같은 학생이 다른 기기로 접속하면 그 기기에서는 다시 "안 읽음"으로 보일 수 있다는 한계가 있다(기기 간 동기화 없음). 서버 동기화까지 하려면 F-62처럼 스키마 변경이 필요해 이번 사이클 스코프를 넘어선다고 판단해 로컬 저장으로 한정.

**검증 조건**
- [x] `npx tsc --noEmit`과 `npm run build` 통과.
- [x] Playwright로 실제 컴파일된 CSS를 사용해 (배지 있음/탭이 활성화되어 배지 없음) 두 상태 렌더링 확인.

**판단 보류 (다음 사이클 후보)**

### F-67: 오늘의 학습 요약에 핵심어 강조 표시

**한 줄 설명:** AI가 생성하는 학습 요약의 각 항목에서 가장 중요한 핵심어 1개를 굵게 강조해, 훑어 읽어도 중요한 부분이 먼저 눈에 들어오게 한다.

**사용자 입력**
- 별도 입력 없음 — 학습 콘텐츠가 생성될 때 자동으로 반영됨.

**시스템 처리**
1. `services/gemini.ts`의 두 콘텐츠 생성 프롬프트(초기 커리큘럼 생성/일일 학습 콘텐츠 생성) 모두에 "각 항목에서 가장 중요한 핵심어 1개만 `**이렇게**` 마크다운 굵게 표시(과하게 여러 개 표시하지 말 것)" 지시를 추가.
2. `LearningScreen.tsx`에 `renderWithBold()`를 추가 — `**...**`로 감싼 부분만 딱 처리하는 최소 마크다운 파서(범용 마크다운 지원이 아님). 각 요약 줄을 렌더링할 때 이 함수를 거쳐 굵게 강조된 `<strong>`으로 바꾼다.
3. 음성 재생(TTS) 경로에서는 `**` 마커가 "별표 별표"처럼 소리 내어 읽히지 않도록 `stripBoldMarkers()`로 마커만 제거한 순수 텍스트를 사용한다.
4. 불릿 접두사(`•`/`·`/`-`/`*`)를 떼어내는 기존 정규식이 `**핵심어**`가 항목 맨 앞에 올 때 앞쪽 `*` 하나만 불릿으로 오인해 잘못 떼어내는 버그가 생길 수 있어(`*(?!\*)`로 "다음이 또 *가 아닐 때만" 단독 `*`를 불릿으로 인정하도록) `stripBulletPrefix()`로 통일해 세 곳(재생/재생속도 변경/화면 렌더링) 모두 같은 안전한 로직을 쓰게 했다.

**사용자 출력**
- 학습 화면의 "오늘의 핵심 내용" 각 항목에서 가장 중요한 단어/문구가 포인트 컬러로 굵게 보인다. 음성으로 들을 땐 평소와 똑같이 자연스러운 문장으로 들린다(마커가 소리로 안 들림).

**동작 규칙**
- 리서치(Mayer의 신호화 원칙, 메타분석 효과크기 d=0.52, 특히 사전지식이 적은 학습자에게 효과적)에 따라 "신호는 과하게 쓰면 안 된다"는 경고를 그대로 반영해 항목당 핵심어 1개로 제한했다.
- 이 기능은 AI가 새로 생성하는 콘텐츠에만 적용된다 — 이미 캐시된 콘텐츠 풀(`contentPool`)이나 문제 은행(`questionBank`)의 기존 텍스트, `data/curriculum.ts`의 사람이 직접 쓴 커리큘럼 텍스트는 그대로 `**` 없이 나오며, 렌더러는 `**`가 없으면 그냥 평범한 텍스트로 처리하므로 문제없이 공존한다.

**검증 조건**
- [x] `npx tsc --noEmit`, `npm run build`, `npm run lint`(기존 11건 지적에서 늘지 않음) 통과.
- [x] Node로 5가지 대표 케이스(맨 앞 굵게/중간 굵게/굵게 없음/단독 `*` 불릿+맨 앞 굵게/대시 불릿+굵게)를 시뮬레이션해 불릿 제거·굵게 파싱·TTS용 마커 제거가 모두 의도대로 동작함을 확인.
- [x] Playwright로 실제 컴파일된 CSS를 사용해 렌더링 확인.
- [ ] 실제 Gemini API가 지시를 얼마나 잘 따르는지(정말 항목당 1개만 표시하는지)는 실제 API 키로 콘텐츠를 생성해봐야 확인 가능 — 이 환경엔 실제 API 호출을 재현할 수 없어 프롬프트·파싱 로직 검증까지만 완료.

**판단 보류 (다음 사이클 후보)**
- AI가 지시를 안 지키고 굵게 표시를 아예 안 하거나 너무 많이 할 경우의 방어 로직(예: 굵게 표시가 3개 넘으면 무시)은 실제 사용 데이터를 보고 필요성을 판단할 다음 사이클 후보.

### F-68: 폼/API 에러 메시지를 스크린 리더가 즉시 읽도록 개선

**한 줄 설명:** 폼 검증·API 실패 시 나타나는 빨간 에러 메시지가 지금까지 스크린 리더 사용자에게 전혀 알려지지 않았다 — `role="alert"`를 붙여 메시지가 뜨는 즉시 자동으로 읽히게 한다.

**사용자 입력**
- 별도 입력 없음 — 기존에 에러가 발생하던 상황(폼 검증 실패, API 호출 실패 등) 그대로.

**시스템 처리**
1. `grep -rniE "text-red-[456]00"`로 코드베이스 전체를 훑어, 실제로 동적 에러 상태(`useState`로 관리되는 `error`류 변수)에 묶인 메시지와 정적 스타일링(마감 지남 라벨, 정답/오답 표시, 필수 입력 별표 등)을 구분했다 — 후자는 `role="alert"`를 붙이면 오히려 잘못된 사용(계속 존재하는 콘텐츠에 "방금 발생한 경보"용 role을 쓰는 것)이라 제외.
2. 실제 동적 에러 변수 11개(`error`×6, `aiError`, `qError`, `saveError`, `materialError`, `feedbackError`)가 렌더링되는 12곳(한 파일에 에러 화면 전체를 감싸는 경우 포함)에 `role="alert"`를 추가 — 8개 파일(`GoalCreateScreen`, `AssignmentCreateScreen`×3, `ClassDetailScreen`, `JoinClassScreen`, `TeacherHomeScreen`, `TeacherOnboardScreen`, `LearningScreen`, `VoiceRecorder`×2).
3. `LearningScreen.tsx`는 에러 시 화면 전체가 에러 안내로 바뀌는 구조라, 메시지 `<p>` 하나가 아니라 그 전체를 감싸는 컨테이너에 `role="alert"`를 붙여 제목+설명이 함께 한 번에 안내되게 했다.

**사용자 출력**
- 시각적으로는 아무 변화 없다(이미 빨간 텍스트로 눈에 띄게 돼 있었음). 스크린 리더 사용자는 에러 메시지가 화면에 나타나는 순간 포커스 이동 없이도 자동으로 그 내용을 듣게 된다.

**동작 규칙**
- 정적으로 항상 존재하는 빨간 텍스트(마감 지남 라벨, 필수 입력 표시 `*`, 정답/오답 색상 구분)에는 붙이지 않았다 — `role="alert"`는 "방금 새로 나타난, 즉시 알려야 할 상태 변화"에만 쓰는 게 올바른 사용이고, 항상 있는 콘텐츠에 붙이면 오히려 스크린 리더가 불필요하게 반복 안내하거나 오용으로 간주될 수 있다.

**검증 조건**
- [x] `npx tsc --noEmit`, `npm run build`, `npm run lint`(기존 11건 지적에서 늘지 않음) 통과.
- [x] Playwright의 `page.getByRole('alert')`로 `role="alert"` 요소가 실제 접근성 트리에 정확히 노출되는지 정적 HTML로 검증(2개 모두 정상 인식).
- [ ] 이 8개 화면 모두 로그인/학원 참여가 필요해 이 세션에서 실제 앱 위에서 에러를 발생시켜 확인할 수는 없었다 — 문법적 정확성(속성 존재·접근성 트리 노출)까지만 검증.

**판단 보류 (다음 사이클 후보)**
- 성공 메시지(예: "저장했어요")에는 `role="status"`(assertive가 아닌 polite)를 붙이는 대칭적 개선도 있을 수 있으나, 이번 사이클은 에러로 스코프를 한정했다 — 다음 사이클 후보.

### F-69: 폼 입력 라벨을 입력창에 프로그래밍적으로 연결

**한 줄 설명:** 폼의 `<label>`이 시각적으로만 입력창 옆에 있었을 뿐 `htmlFor`/`id`로 실제 연결돼 있지 않았다 — 스크린 리더 사용자가 입력창에 포커스했을 때 "학습 주제" 같은 라벨을 들을 수 있게 연결한다.

**사용자 입력**
- 별도 입력 없음 — 화면 구조 개선.

**시스템 처리**
1. `grep -rln "<label"`으로 라벨을 쓰는 화면 6개(`GoalCreateScreen`, `GoalEditScreen`, `AssignmentCreateScreen`, `ClassDetailScreen`, `TeacherHomeScreen`, `TeacherOnboardScreen`)를 찾고, `htmlFor` 사용이 0건임을 확인했다.
2. 라벨 14개를 하나씩 확인해 두 유형으로 분류: (a) 입력을 라벨 안에 감싸는 방식(체크박스 등 — 이미 암묵적으로 연결돼 있어 손댈 필요 없음), (b) 라벨과 입력이 형제 요소로만 나란히 있는 방식(연결 안 됨).
3. (b) 유형 9곳에 `htmlFor`/`id` 쌍을 추가 — 학습 주제·기한·참고자료(목표 생성/수정), 숙제 제목·마감일, 수업자료 파일 첨부, 반 이름, 학원 초대 코드.
4. `GoalCreateScreen`의 "난이도" 라벨(버튼 그룹을 위한 그룹 제목이지 특정 입력 하나를 가리키지 않음)과 `GoalEditScreen`의 "주제" 라벨(읽기 전용 표시용 `<div>`, 실제 입력창 아님)은 `htmlFor`를 붙일 단일 대상이 없어 제외했다.

**사용자 출력**
- 시각적으로는 아무 변화 없다. 스크린 리더 사용자가 Tab으로 입력창에 들어가면 "학습 주제, 편집 가능한 텍스트" 처럼 라벨과 함께 안내된다.

**동작 규칙**
- 입력을 라벨로 감싸는 기존 패턴(체크박스 목록 등)은 이미 올바른 접근성 패턴이라 건드리지 않았다 — `htmlFor`/`id`를 추가로 붙이는 건 불필요한 중복.
- 그룹 라벨(예: "난이도")처럼 단일 입력에 대응하지 않는 경우 억지로 `htmlFor`를 붙이지 않았다 — 잘못된 대상에 연결하면 오히려 혼란을 준다.

**검증 조건**
- [x] `npx tsc --noEmit`, `npm run build`, `npm run lint`(기존 11건 지적에서 늘지 않음) 통과.
- [x] Playwright의 `page.getByLabel(...)`로 `htmlFor`/`id` 연결이 실제로 동작해 라벨 텍스트로 입력창을 찾을 수 있는지 정적 HTML로 검증(2개 모두 정상 인식).

**판단 보류 (다음 사이클 후보)**
- `SettingsScreen`처럼 아직 안 훑어본 폼이 더 있을 수 있어, 이번엔 `<label>` 태그를 실제로 쓰는 화면만 다뤘다 — placeholder만 있고 `<label>` 자체가 아예 없는 입력창이 있는지는 다음 사이클에서 별도 확인 필요.
