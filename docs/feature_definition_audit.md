## 1. 추가 후보 검증

### A-1. 목표 중단 → 재개 허용

**현재 코드 확인**: `GoalListScreen.tsx`의 `GoalItem`은 `goal.status === 'active'`일 때만 "학습하기/수정/중단" 버튼을 보여주고, `status !== 'active'`(즉 `inactive` 또는 `completed`)일 때는 **삭제 버튼만** 보여준다(147-186행). `inactive` 상태를 다시 `active`로 되돌리는 버튼/핸들러는 **어디에도 없다**. `GoalEditScreen.tsx`도 상태(`status`)를 다루지 않고 `deadline`만 수정 가능. `handleDeactivate`(199-204행)는 `updateGoal({...goal, status: 'inactive'})`만 하고 역방향 함수는 없다.

데이터 계층(`store/index.ts`의 `updateGoal`, `utils/storage.ts`의 `saveGoal`)은 상태값에 아무 제약을 걸지 않는 범용 함수라, **재활성화를 막는 것은 순수하게 UI 레이어의 부재**이지 데이터 모델이나 저장 로직의 제약이 아니다. `GoalStatus` 타입(`types/index.ts:1`)도 `'active' | 'completed' | 'inactive'`로 이미 양방향 전이가 표현 가능한 타입이다.

**구현 지점(구체)**:
1. `GoalListScreen.tsx`의 `GoalItem`에 `goal.status === 'inactive'`일 때 "재개" 버튼 추가, `onReactivate(goal.id)` 콜백 연결.
2. `GoalListScreen`의 `handleDeactivate` 옆에 `handleReactivate = (id) => updateGoal({...goal, status: 'active'})` 추가.
3. **주의**: 중단 기간 중 `deadline`이 이미 지났을 수 있음. 재개 시 `deadline <= today`이면 그대로 `active`로 돌리면 `DaysLeft`가 "마감 지남"을 표시한 채로 활성 목표가 되는 모순 상태가 됨. → 재개 버튼은 `GoalEditScreen`으로 라우팅해 기한을 먼저 갱신하게 하거나(기존 "기한 지나면 저장 불가" 로직 재사용), 재개 시점에 자동으로 `totalSessions`를 오늘 기준 재계산해야 함.
4. 스트릭(`streak`)은 재개 시 0으로 리셋할지 유지할지 정책 결정 필요(코드에 자동 처리 없음 — `handleDeactivate`가 스트릭을 건드리지 않으므로 현재는 그대로 남아있다가, 재개 후 다음 세션에서 이어질 수 있음. "며칠 쉬었는데 스트릭이 그대로"인 게 맞는지는 제품 판단 필요).

**결론**: Planner 주장("재활성화 완전 차단")은 코드로 확인됨. 구현 자체는 간단하지만 **기한/스트릭 처리 정책은 사람 확인 필요**.

### A-2. PWA 설치 유도

`manifest.json` 존재 여부, `vite.config`의 PWA 플러그인 여부는 이번 세션에서 미확인(범위 밖 — Planner가 제안만 했고 코드 존재를 주장하지 않음). 별도 조사 필요하나 우선순위상 A-1/A-5보다 낮음. 신규 기능이라 "안전"보다는 "구현 후 검토" 대상.

### A-3. 5분 카운트다운 시각 표시

**확인**: `LearningScreen.tsx:301`에 `{dayNum}일째 / 전체 {goal.totalSessions}일 · 약 5분` — 정적 텍스트만 존재, 타이머 없음. `TestScreen.tsx`에도 "약 5분" 문자열 없음(grep 결과 0건) — 즉 테스트 화면에는 그 문구조차 없다.
**구현 지점**: `LearningScreen.tsx`(요약 열람)와 `TestScreen.tsx`(퀴즈 응답)에 각각 `useState` + `setInterval(1000)` 경과시간 카운터 추가. 신규 의존성 불필요. **주의**: `TestScreen.tsx`에 이미 `useEffect`로 세션 종료/네비게이션 처리하는 로직이 있으므로(오답 풀 갱신, XP 계산 등) 타이머의 `useEffect` cleanup을 놓치면 언마운트 후 메모리 누수 가능 — 신규 `useEffect`는 반드시 `clearInterval` 반환.

### A-4. 다중 목표 "오늘 할 일" 자동 추천

이미 `UrgentBanner`(HomeScreen.tsx:172-234)가 지연 목표를 배너로 우선 노출하는 기능을 갖고 있음 — Planner가 "재사용해 정렬 기준만 추가하면 됨"이라 한 것은 맞으나, **정확히는 재사용이 아니라 확장**: 지금은 배너(요약 알림) + 카드 전체 나열이 공존하는 구조이고, A-4가 요구하는 "카드 자체를 접어서 하나만 크게" 레벨의 변경은 `HomeScreen.tsx:332`의 `activeGoals.map(...)` 렌더링 로직을 통째로 바꿔야 함(단순 정렬 아님 — 접기/펼치기 상태 관리 추가 필요).
**추가 발견**: F-01 검증조건에 명시된 "활성 목표 3개 제한"이 코드에 미구현(§0 참고). 목표 카드가 이론상 무제한으로 늘어날 수 있어 A-4의 필요성은 오히려 Planner 서술보다 크다.

### A-5. 오답 풀 필터 범위(active만 노출)

**확인**: `WrongPoolScreen.tsx:12-14` — `goals.filter((g) => g.status === 'active')`. Planner 주장 그대로 확인됨. 목표를 "중단"하거나 "완료"하는 즉시 그 목표의 오답 섹션이 `WrongPoolScreen`에서 사라진다.
**제품 판단**: 이건 "버그"보다는 **"설계 결정이 문서화 안 된 것"**에 가깝다 — `completed`(목표 완주)의 오답을 계속 복습시키는 것은 F-13("오답을 부드럽게 다시 보여준다") 취지에 부합하지만, `inactive`(중단)의 오답까지 노출하는 것은 "중단한 목표"를 자꾸 상기시켜 오히려 이탈 요인이 될 수 있어 **`completed`는 포함, `inactive`는 제외**가 더 안전한 기본값으로 보인다.
**구현 지점**: `WrongPoolScreen.tsx:13`의 필터를 `g.status === 'active' || g.status === 'completed'`로 변경. 1줄 수정.

## 2. 제거/축소 후보 검증

### P-1. 목표 생성 화면 옵션 과잉

| 항목 | F-02 원문 문언 | quizCount(F-44)와의 관계 |
|---|---|---|
| "하루 학습 분량은 5분 완결 기준으로 자동 조율된다" | 매일 테스트 문항 수는 **여전히 5개 고정**(`GoalCreateScreen.tsx:300` 주석) | 위반 아님 |
| "사용자가 분량을 직접 늘리거나 줄이는 설정은 제공하지 않는다" | quizCount는 "생성될 전체 문제 풀 크기"(반복 없이 더 오래 풀 수 있는 총량)를 사용자가 고름 | **문언의 정신과는 충돌** — "분량"을 하루 노출량이 아니라 총량으로 넓게 해석하면 위반 |

**현실적 선택지 (Planner 요청대로 "되돌리자"가 아니라)**:
1. **문서 갱신안**: F-02에 "단, 총 문제 풀 크기(반복 주기)는 사용자가 조절 가능하다"는 예외 조항 추가. 코드 변경 없음, 문서 부채만 해소.
2. **옵션 축소안**: `QUIZ_COUNT_OPTIONS`을 4단계(5/10/15/20)에서 2단계(5/10) 정도로 줄여 "게으른 사람"의 선택 부담을 낮추되 기능 자체는 유지.
3. **숨김안**: 기본값 5 유지, "더보기" 아코디언 뒤로 감춰 최초 노출 항목 수를 6개→5개로 줄임.

세 안 모두 **되돌리는 안(A-1처럼 롤백)은 포함하지 않음** — 최근 사용자 명시 요청 기능이므로. **최종 선택은 사람 확인 필요.**

### P-2. 완료 화면 조건부 블록 과밀

**SessionCompleteScreen.tsx 조건부 블록 실측 (7개)**:

| 블록 | 조건 | 상호배타 여부 |
|---|---|---|
| 레벨업 배너 | `didLevelUp` | 뱃지·깜짝보상과 동시 가능 |
| XP 카운트업 | `xpGained > 0` | 거의 항상 참(웬만하면 XP 획득) — 사실상 상시 노출 |
| 성장피드백 | `growthFeedback` 존재 | 위와 동시 표시 가능 |
| 프리즈 안내 | `usedFreeze` | 독립 |
| 깜짝 보상 | `surpriseReward` | **뱃지·레벨업과는 코드로 상호배타 처리됨**(`TestScreen.tsx:311-313`) |
| 마일스톤 정체성서사 | `isStreakMilestone`(flame_7 또는 persistence_30 뱃지) | 뱃지 블록과 동시 표시(뱃지 목록에도 같은 뱃지가 또 나옴 — **사실상 중복 노출**) |
| 뱃지 목록 | `newBadges.length > 0` | 위 참고 |

`GoalCompleteScreen.tsx`는 5개(레벨업/XP/성장피드백/정체성서사(거의 상시, `goal` 존재 시)/뱃지) — 세션 완료보다는 적음.

**실제 최악 케이스**: 스트릭 마일스톤 달성 + 레벨업 + 만점(성장피드백 personal best) + 프리즈 사용 이력 + 뱃지 획득이 겹치면 **레벨업, XP, 성장피드백, 프리즈, 마일스톤서사, 뱃지 6블록이 동시 노출** 가능(깜짝보상만 상호배타로 빠짐). 자동 이동은 6초 뒤(레벨업 있으면) — 이 정보량을 6초 안에 다 읽기는 실제로 무리.

**구현 가능한 우선순위 로직 제안** (레벨업 > 마일스톤서사 > 뱃지 > 자기최고기록 > 프리즈 > XP):

```
표시 후보를 배열로 만들고 우선순위 상위 2개만 mb-4로 렌더, 나머지는 상단 요약 배지(작은 아이콘 한 줄)로 축약
예: [didLevelUp, isStreakMilestone, newBadges.length>0, growthFeedback?.isPersonalBest, usedFreeze]
   .filter(Boolean).slice(0, 2)  // 상위 2개만 전체 블록, 나머지는 한 줄 요약
```
마일스톤 정체성서사와 뱃지 목록이 같은 뱃지를 중복 언급하는 것(flame_7/persistence_30)은 **버그에 가까운 중복**이므로 우선순위와 별개로 먼저 손볼 가치 있음.

### P-3. 오답목록 / 오답다시풀기 / 내 문제집

| `MyQuestionBookScreen` | 사용자가 수동 북마크한 문제 모음(읽기 전용) | `quizzes.filter(q => q.bookmarked)` | 목표별 섹션 → 카드 리스트(질문/정답/해설) — **WrongPoolScreen과 골격 100% 동일** |
| `RetryWrongScreen` | 오답을 실제로 다시 풀어보는 **인터랙티브 세션** | `getActiveWrongPool` + `QuizCard` 채점 | TestScreen과 동급의 단일 문제 진행형 화면(진행바, 정답 처리, 완료 화면 포함) |

**정정된 결론**: "3화면 중복"이 아니라 **읽기 전용 리스트 2개(오답목록·내문제집)가 겹치고, 다시풀기는 목적이 명백히 다른 별개 기능**이다. 통합을 검토한다면 대상은 `WrongPoolScreen` + `MyQuestionBookScreen`만 — 탭(오답/북마크) 전환 UI로 합치고 "다시 풀기" 버튼은 오답 탭에서만 노출하면 큰 손실 없이 화면 1개, 설정 메뉴 링크 1개(2→1) 절감 가능. `RetryWrongScreen`은 그대로 유지.
**단정 보류**: 실사용 로그가 없어 "그래도 사용자가 둘을 구분해서 쓴다"는 가능성 배제 못함. **사람 확인 필요.**

### P-4. 확률적 깜짝 보상(F-39)

`surpriseReward.ts` 확인: 메시지 뱅크는 톤별 3종씩, 결제/가챠 요소 전혀 없음. `TestScreen.tsx:311-313`에서 뱃지·레벨업 세션과 상호배타 처리가 **이미 구현돼 있어** Planner가 우려한 "완료 화면 과밀에 기여"는 실제로는 제한적(뱃지·레벨업 세션에는 아예 안 뜸 — 즉 화면이 이미 복잡한 순간엔 발동 안 함, 오히려 설계가 괜찮음). 다만 "운으로 받는 보상"이라는 정체성 정합성 이슈는 여전히 유효한 별개 논점.
**결론**: P-2보다 우선순위 낮음. 제거보다는 "유지, 재검토는 나중"이 합리적.

### P-5. mateTone 톤 인프라

`mateTone`/`MateTone` 사용처 14개 파일(`QuizCard`, `GoalCreateScreen`, `gemini.ts`, `HomeScreen`, `TestScreen`, `GoalCompleteScreen`, `SessionCompleteScreen`, `RetryWrongScreen`, `mascot.ts`, `streakCrisisMessage.ts`, `surpriseReward.ts`, `LearningScreen`, `notification.ts`, `types/index.ts`) — Planner 주장대로 이미 제품 전반에 깊게 얽혀 있음. 지금 걷어내는 것은 오히려 blast radius가 크다(14개 파일 수정 필요). **실사용 비율 확인 전에는 손대지 않는 게 안전** — Planner 판단에 동의.

### P-6. 하단 탭 "업적"

`BottomNav.tsx` 확인: 탭 4개(홈/목표/업적/설정) 그대로 하드코딩. "업적" 탭만 핵심 루프(목표→학습→테스트→완료)와 무관. 탭에서 빼고 설정/홈 진입점으로 격하하는 것은 **`BottomNav.tsx`의 `tabs` 배열에서 항목 제거 + 진입 경로 하나 추가**로 구현 자체는 단순. 다만 **사용자 습관(이미 학습된 탭 위치)에 영향** → UX 변경이라 사람 확인 필요.

### P-7. 녹음 모음(RecordingsScreen)

`RecordingsScreen.tsx` 확인: `voiceRecording.ts`의 `getAllRecordings`/`deleteRecording`로 블롭 저장(IndexedDB로 추정), 재생용 `URL.createObjectURL` 생성/정리 로직 존재. 최근 커밋(`cd9a674`)으로 막 추가된 기능이라 사용 이력 자체가 없음(배포 직후). Planner 말대로 문서화가 전혀 안 됐고, 목적(자기 답변을 육성으로 복기?)이 코드 주석 수준에서도 불명확. **제거하기엔 너무 이르다(막 추가됨) — 지금은 "관찰" 단계가 맞고, 문서화(기능정의서에 F-46 항목 추가)부터가 우선.**
